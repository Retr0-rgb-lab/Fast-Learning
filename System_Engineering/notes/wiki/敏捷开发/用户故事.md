# 用户故事 · User Stories

> **一句话**：在 XP 中，用户需求用**用户故事**表达 —— 一段**非正式、自然语言**的、对系统某项功能的描述。三个 C 规定了它的生命周期：写成卡片、与人讨论、与客户确认。

课件原文见 [03. Agile Software Development](<../../raw/03. Agile Software Development.pdf>)。所属原则见 [[敏捷宣言与原则]]。

## 是什么

**用户故事 = 对软件系统某项功能的非正式自然语言描述。**

它**不是**系统规格说明。课件明确指出：用户故事**是用户需求，但不是系统需求**，因为它们常常遗漏关于系统的重要信息。

> [!warning] 直接后果
> 因为用户故事不是系统规格，**没有一个外部测试团队能用它来开发系统测试**。这是 XP 自建测试方法的原因，见 [[测试驱动开发]]。

## 常见格式

```
As a <role> I can <capability>, so that <benefit>
```

```
As <who> <when> <where>, I want <what> because <why>
```

## 三个 C · The Three C's

| C | 英文 | 含义 |
|---|---|---|
| **1** | **Card** | 故事的**书面描述**，写在卡片上，用于**计划（planning）和估算（estimation）** |
| **2** | **Communication** | **与他人讨论**这个想法 |
| **3** | **Confirmation** | 与相关方**就"要做什么"达成一致**（reach an agreement on what to build） |

> 三个 C 是一条**链**：先写下来 → 再拿出去讨论 → 最后确认。三步都不可省。

## 优点与缺点

**优点**：人们**比起传统需求文档或用例，更容易理解**这些故事。

**缺点**：**很难判断**已经开发的故事是否足以覆盖所有必要需求，也**很难判断**单个故事是否真实反映了一项完整活动。

> [!tip] 怎么补这个缺点
> 这正是敏捷方法**同时需要客户参与**和**持续增量交付**的原因 —— 覆盖度不是靠一次写全，而是靠每个迭代的评审逐步确认。见 [[敏捷宣言与原则]]。

## 与"设计变更"的关系

课件提出一个与常识相反的对比：

| 立场 | 主张 |
|---|---|
| 传统工程智慧 · **Design for change** | 值得投入时间**预判变化**，因为这能降低生命周期后期的成本 |
| XP 立场 | 改为**持续改进代码**（**重构**，refactoring），在变化必须实现时让它更容易。"Design for change" **不值得做**，因为**变化无法被可靠地预判** |

详见 [[重构]]。
