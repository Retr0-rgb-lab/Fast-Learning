# 结对编程与集体所有 · Pair Programming & Collective Ownership

> **一句话**：**两名程序员坐在同一台电脑前一起开发**。配对是**动态形成**的，目标是让所有团队成员在开发过程中都彼此接触，从而支撑**集体所有权**。

课件原文见 [03. Agile Software Development](<../../raw/03. Agile Software Development.pdf>)。所属原则见 [[敏捷宣言与原则]]。

## 结对编程 · Pair Programming

程序员**坐在一起用同一台电脑**开发软件。

**配对是动态创建的（created dynamically）**，使得**所有团队成员在开发过程中都与彼此协作过**。

### 收益

| 收益 | 说明 |
|---|---|
| 支撑**集体所有权**与对系统的**共同责任** | 知识不集中在单个人手里 |
| 充当一种**非正式的评审（informal review）** | 因为**至少有两个人**在看每一行代码 |
| **鼓励重构**以改善软件结构 | 有人在旁边看，就没人会写下明知很烂的代码 |

> [!tip] 常见误解
> 课件明确说：它**不一定低效**（it is not necessarily inefficient）。
>
> 反对"两个人干活比一个人慢"的直觉：单人产出的代码常常无人评审、结构劣化；成对产出的代码**更干净**，且**没有巴士系数（bus factor）为 1** 的风险。

## 集体所有 · Collective Ownership

**各配对在系统的所有区域上工作**，因此：

- **不会形成"专家孤岛"**（no islands of expertise）
- **所有开发者对所有代码负责**
- **任何人都可以修改任何东西**（Anyone can change anything）

## XP 原则与实践全表

| 原则 / 实践 | 说明 |
|---|---|
| **Incremental planning** 增量式计划 | 需求记录在**故事卡（story cards）**上；选哪些故事进一个发布，由**可用时间**和**相对优先级**决定 |
| **Small releases** 小版本发布 | 先开发**提供商业价值的最小可用功能集**。系统发布频繁，并以增量方式在首个版本上叠加功能 |
| **Simple design** 简单设计 | 只做**足以满足当前需求**的设计，**不多做** |
| **Test-driven development** 测试驱动开发 | 先写失败的自动化测试，再写刚好让它通过的生产代码，最后在保持测试全绿时重构 |
| **Refactoring** 重构 | 一发现可能的代码改进就**立即**重构，保持代码简单可维护 |
| **Pair programming** 结对编程 | 开发者成对工作，互相检查、互相支持 |
| **Collective ownership** 集体所有 | 配对在系统所有区域工作，避免专家孤岛，人人负责全部代码 |
| **Continuous integration** 持续集成 | 任务一完成**立即集成**进整个系统；**任何一次集成之后，全系统的单元测试必须通过** |
| **Sustainable pace** 可持续节奏 | **不接受大量加班** —— 其净效果通常是**降低代码质量和中期生产率** |
| **On-site customer** 现场客户 | 最终用户的**代表（客户）应全职**可用于 XP 团队 |
