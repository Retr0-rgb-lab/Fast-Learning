# 测试驱动开发 · Test-Driven Development

> **一句话**：**先写测试程序，再写代码。** 测试先写避免了"测试滞后（test-lag）"问题，并**隐式地定义了该功能的接口与行为规格**。

课件原文见 [03. Agile Software Development](<../../raw/03. Agile Software Development.pdf>)。所属原则见 [[敏捷宣言与原则]]。

## 为什么先写测试

| 理由 | 说明 |
|---|---|
| 避免 **test-lag** | 测试总是滞后于实现，于是测试追着实现跑，测的是"代码做了什么"而非"应该做什么" |
| **隐式定义规格** | 先写测试**同时定义了功能的接口和行为规格** —— 写测试的过程就是在说清"这个功能要怎样" |

每个测试都**包含对其执行结果是否正确的检查**。

**每加入新功能时，所有既有测试和新测试都会被自动运行**，以检查新功能**没有引入错误**。通常依赖一个**测试框架**（如 **JUnit**）。

> [!tip] 标准表述
> 课件的实践定义：写一个**失败的**自动化测试 → 写**刚好让它通过**的代码 → 在保持所有测试绿色的同时**重构**。（red → green → refactor）

## XP 测试的四个特点

1. **从场景出发，增量地开发测试**（Incremental test development from scenarios）
2. **测试驱动开发**（Test-driven development）
3. **客户参与**测试的开发与确认（Customer involvement in test development and validation）
4. **使用自动化测试框架**（Use of automated testing frameworks）

## 客户在测试中的职责

**客户帮助开发验收测试（acceptance tests）**，用于下一个发布版本要实现的用户故事。

**局限**：

- 承担客户角色的人**时间有限**，无法全职与开发团队一起工作。
- 他们可能认为**"提供了需求就已经尽到贡献了"**，因而**不愿参与测试过程**。

## 测试自动化 · Test Automation

**测试自动化** = 测试被写成**可执行的组件**，且**在被测任务实现之前**就写好。

这些测试组件应当：

- 是**独立可运行的**（stand-alone）
- **模拟待测输入的提交**
- **检查结果是否满足输出规格**

**自动化测试框架**（如 JUnit）= 使编写可执行测试变得容易、并能提交一组测试执行的系统。

因为测试是自动化的，所以**总有一套可以被快速、轻松执行的测试**。每当系统加入任何功能，就可以运行这些测试，**由新代码引入的问题能被立即发现**。

## 测试驱动开发的困难

| 困难 | 例子 |
|---|---|
| 程序员**偏好编程而非测试**，有时写测试时**抄近路** | 写出不完整的测试，不检查所有可能发生的异常 |
| 某些测试**很难增量地写出来** | 在各个组件尚未建好之前，为复杂的多步用户旅程写 **E2E 测试** |
| **难以判断一组测试的完整性** | 可能有大量系统测试，但**并未提供完整覆盖** |

> [!important] 与 Verification/Validation 的关系
> TDD 的测试是**开发者自己、在实现之前**写的自动化单元/系统测试 —— 这与 [[软件过程-四活动]] 中"validation 只能由外部团队事后做"的误解正相反。TDD 证明"用户故事不足以支持外部测试团队"（见 [[用户故事]]）这个前提正是 XP 发展出这套方法的原因。
