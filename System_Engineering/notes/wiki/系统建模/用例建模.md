# 用例建模 · Use Case Modelling

> **一句话**：**用例图**（椭圆）表示系统与**外部 actor**（人或系统）之间的交互。两条虚线关系最难区分：**`<<include>>` 是强制依赖**（无条件的共用步骤），**`<<extend>>` 是条件追加**（可选的附加行为）。

课件原文见 [05. System Modelling](<../../raw/05. System Modelling.pdf>)。所属视角见 [[系统建模-定义与视角]]。

## 两个元素

- **用例（use case）= 椭圆**，表示一项**涉及与系统外部交互的离散任务**。
- **actor（角色）= 火柴人**，**可以是人，也可以是系统**。

## 交互建模的三个用途

| 建模对象 | 揭示什么 |
|---|---|
| **用户交互** | 帮助**识别用户需求** |
| **系统到系统的交互** | 突显可能出现的**通信（communication）问题** |
| **组件之间的交互** | 帮助理解**所提出的系统结构是否能满足所需的性能与可依赖性** |

## 两类关系 · include 与 extend

| 关系 | 应用在 | 箭头样式 | 目的 |
|---|---|---|---|
| **关联 Association** | Actor ↔ Use case | 实线 | 连接 actor 与其参与的交互 |
| **泛化 Generalization** | Use case → Use case | 实线 + 空心三角 | 特化通用行为（多态/继承） |
| **Actor 泛化 Actor generalization** | Actor → Actor | 实线 + 空心三角 | 创建 actor 的特化角色/权限 |
| **`<<include>>`** | Use case → Use case | 虚线，标 `<<include>>` | **复用共用的必需执行步骤** |
| **`<<extend>>`** | Use case → Use case | 虚线，标 `<<extend>>` | **为基础流程添加可选或条件性步骤** |

### `<<include>>` —— 强制依赖

**含义**：**基础用例需要另一个用例才能完成其操作。**

**用途**：把**多个用例共有的步骤序列**抽取为**可复用的单元**。

- **基础用例**：提现现金、查询余额
- **被包含的用例**：**认证用户**
- 因为"提现"和"查余额"**都必须**先认证，所以**认证用户**被 `<<include>>`。

### `<<extend>>` —— 条件追加

**含义**：一个用例**在特定条件下（定义在 extension point 上）为基础用例追加行为**。**基础用例可以独立成功完成，从不触发该扩展。**

- **基础用例**：提现现金
- **扩展用例**：**发送余额不足提醒**
- **扩展条件**：仅当**提现后账户余额低于阈值**时触发

> [!important] 两者的判别
> 问一句：**基础用例缺了它还能不能跑完？**
> - **不能** → `<<include>>`（**强制**依赖）
> - **能**，只是可能顺带做一下 → `<<extend>>`（**可选**追加）
>
> **`<<include>>` 不是"更通用"，而是"基础用例对它有强制依赖"。** 它表达的是**必做的共用步骤**，因此常被多个基础用例共同指向。

## 完整示例（自行补全）

一个订单处理系统包含：顾客（Customer）、其特化角色 VIP 顾客（VIP Customer），以及支付网关（Payment Gateway）、一个"申请 VIP 礼宾"（Request VIP Concierge）的扩展。

用例之间的关系是：

- **结账 Checkout** `<<include>>` **认证用户 Authenticate User** —— 必须先认证
- **结账 Checkout** `<<include>>` **为订单付款 Pay for Order** —— 必须付款
- **为订单付款 Pay for Order** **特化**为「信用卡付款」与「PayPal 付款」两个具体用例 —— 用例泛化
- **申请 VIP 礼宾 Request VIP Concierge** `<<extend>>` **为订单付款 Pay for Order** —— 仅当客户是 VIP 时才追加
