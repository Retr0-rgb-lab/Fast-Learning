# 计算图与梯度跟踪

**计算图（computational graph）**：把前向计算拆成一张有向图，反向时按链式法则自动求梯度——[[Autograd 自动微分]] 的实现基础。

## 官方 Autograd 教程那张计算图在画什么

对应代码：

```python
z = torch.matmul(x, w) + b
loss = F.binary_cross_entropy_with_logits(z, y)
```

| 符号 | 含义 |
| :-- | :-- |
| X | 输入（一条样本），不算梯度 |
| W | 权重，要训练，`requires_grad=True` |
| B | 偏置，同样要训练 |
| MATMUL / + | 线性层：$z = xW + b$ |
| Y | 真实标签（ground truth），不算梯度 |
| CE | **Cross Entropy 交叉熵**损失节点，见 [[交叉熵损失]] |
| loss | 标量损失，反向传播从这里开始 |

流程：**X 和 W 相乘，再加 B → 得到预测 z → 和标签 Y 做交叉熵 → 得到 loss。**

- **从左到右（前向）**：数据怎么一步步算出 loss
- **从右到左（反向）**：`loss.backward()` 时，梯度沿同一条路往回传，算出 $\partial L/\partial W$、$\partial L/\partial B$
- CE 不是一个新变量，而是**损失函数节点**；Y 是标签，不是模型算出来的；模型输出是中间的 z（logits，见 [[Logits、Softmax 与 argmax]]）

## Gradient tracking 在记什么

autograd 在前向时**记下每一步运算**，好在 `backward()` 时按链式法则往回求导。`requires_grad=True` 是开关：只有这类张量（以及由它们算出来的中间结果）会被记进计算图。默认 `False`，普通加减乘除不记账——省内存、也更快。

对 `z = x @ w + b` 这类运算，PyTorch 给输出挂上 `grad_fn`（如 `AddBackward0`、`MmBackward0`），指向"这一步怎么反着求导"；一串 `grad_fn` 连起来就是计算历史。

规则很简单：

- **叶子节点**（亲手创建的 `w`、`b`）：标了 `True` 才会被跟踪
- **中间结果**：只要**任意一个输入**要梯度，输出也会 `requires_grad=True` 并带 `grad_fn`；否则整条链断了，loss 回不到权重

所以不是"所有张量都跟踪"，而是：**从可训练参数出发的那条计算路径**会被记录。`loss.backward()` 从 loss 沿 `grad_fn` 往叶子走，只给**叶子且 requires_grad=True** 的张量填 `.grad`。

## requires_grad 怎么用

```python
x = torch.ones(5)                          # 输入，不算梯度
y = torch.zeros(3)                         # 标签，不算梯度
w = torch.randn(5, 3, requires_grad=True)  # 权重，要算梯度
b = torch.randn(3, requires_grad=True)     # 偏置，要算梯度
# 也可以创建后再开：x.requires_grad_(True)
```

- 输入 `x`、标签 `y` 一般**不标**——它们不是要更新的参数
- 不标的后果：前向照样能算，但不建图、不存中间结果，`backward()` 后也没有 `.grad`（更省内存、更快）
- 只有计算图的**叶子节点**且 `requires_grad=True` 才能拿到 `.grad`，中间结果一般没有
- 用 `nn.Linear` 等模块时，内部权重已经是 `nn.Parameter`，默认 `requires_grad=True`，一般不用手写

## 什么时候关掉跟踪

验证、推理不更新参数，不必建图：

```python
with torch.no_grad():        # 整段不算梯度
    ...
z = (x @ w).detach()         # 切断这条边，后面不再连回原图
param.requires_grad = False  # 冻结某层
```

## 图里存的是什么（不是什么）

> [!tip] 一句话
> 每个被追踪的张量记录的是**"我是被哪个函数从哪些输入算出来的"**——是**生成它的操作与来源**，不是它**之前长什么样**。

`backward()` 时从 loss 出发，沿 `grad_fn` 链反向走，每到一个节点就用对应 `Function` 的反向公式算局部导数，再传给上游。所以：

- 不存中间数值快照（数值当场算完就丢，`backward` 时按图重算，或读 `.grad_fn` 调用反向）
- 存的是**算子 + 输入指针**，链起来就是"前向是怎么搭的"
- 因此反向的路径完全镜像正向的路径（拓扑反向）

这也是为什么 `in-place` 操作（`add_`、`x[i] = ...`）会炸——它偷偷改了某节点的"输入"，图里记的来源和实际数值对不上。

## 为什么手动参数更新必须 `no_grad`

参数更新这一行 `w -= lr * w.grad` 本身是 `w` 的函数（因为右侧依赖 `w.grad` 来自前向计算图）。如果让 autograd 追踪它，**反向传播时会多出一条"参数减梯度"的边**——下次 `loss.backward()`，loss 的梯度试图穿过这条边传到 `w`，但这条边和 loss **根本没有函数关系**，纯属污染。

更糟的是：这一步会让 autograd 持续把更新边加到下一次 `上 的图上，循环累积图节点、占内存、还可能算错。

`with torch.no_grad():` 把这一段明确**摘出计算图**：块内操作正常执行，但新产生的张量不带 `grad_fn`，反向不会经过。

```python
with torch.no_grad():
    w -= lr * w.grad        # 执行算术更新，但不进图
w.grad.zero_()               # 清零，下一轮重新累
```

> [!note] 一句话
> 计算图记录"每个张量怎么从输入算出来的"；`no_grad` 把某段操作从图里摘出去，让反向传播**看不见**它。手动参数更新正是这类"不该被 autograd 看到"的操作。
