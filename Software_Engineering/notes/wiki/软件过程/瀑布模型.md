# 瀑布模型 · Waterfall Model

> **一句话**：瀑布模型把项目切成**五个独立标识的阶段**，原则上**一个阶段完成之后才能进入下一阶段**。它是计划驱动过程的典型代表。

课件原文见 [02. Software Processes](<../../raw/02. Software Processes.pdf>)。三种通用模型之一，另两个见 [[增量开发]]、[[复用式软件工程]]。

## 五个阶段

| # | 阶段 | 英文 |
|---|---|---|
| 1 | 需求分析与定义 | Requirements analysis and definition |
| 2 | 系统与软件设计 | System and software design |
| 3 | 实现与单元测试 | Implementation and unit testing |
| 4 | 集成与系统测试 | Integration and system testing |
| 5 | 运行与维护 | Operation and maintenance |

## 核心机制

**阶段之间是单向的、有序的。** 前一阶段的产物是后一阶段的输入。需求在阶段 1 之后原则上不再接收"预期内"的变更 —— 变更要作为新工作提出。

## 难以应对需求变更的原因

**不可逆的阶段切分（inflexible partitioning of the project into distinct stages）。**

因为需求在开发过程中**本来就会变**（课件称为 **moving target problem**，见 [[应对变更]]），而阶段 1 一结束，需求就被"冻结"了。此后任何需求变更都会引发**返工**：设计要改、代码要改、测试要重写，已完成的工作大量作废。

因此：

> **瀑布模型只在"需求已被充分理解、且设计期间变更相当有限"时才适用。**

而课件明确指出：**很少有业务系统的需求是稳定的。**

## 适用的三类系统

| 系统类型 | 为什么适合 |
|---|---|
| **嵌入式系统**（embedded systems） | 软件必须与**硬件系统**对接，接口在设计前就必须定死 |
| **关键系统**（critical systems） | 需要对软件规格与设计做**大量的安全与安全性分析**（extensive safety and security analysis） |
| **大型系统**（large systems） | 属于由**多家合作公司**共同开发的更大工程系统的一部分，需要严格的前期约定 |

> [!tip] 共同点
> 这三类系统的共同前提是：**功能边界在开发前已确定、变更代价极高**。嵌入式受硬件牵制，关键系统受安全法规约束，大型多方系统受合同约束。
