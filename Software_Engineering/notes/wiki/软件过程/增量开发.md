# 增量开发与增量交付

> **一句话**：增量开发的思想是**先做出一个初始实现，从用户处获得反馈，再让软件经过若干版本的演化，直到系统被完整开发出来**。它可以是计划驱动的、敏捷的，或更常见的**两者的混合**。

课件原文见 [02. Software Processes](<../../raw/02. Software Processes.pdf>)。另两个通用模型见 [[瀑布模型]]、[[复用式软件工程]]。

> [!important] 关键澄清
> **增量 ≠ 交付。** 增量开发中，**你不必把每一个 increment 都交付给系统客户**（you don't have to deliver each increment to the system customer）。两者是相关但独立的概念。

## 增量交付 Incremental Delivery

**开发与交付被拆成若干 increment，每个 increment 交付一部分所需功能。**

- 用户需求被**排序（prioritised）**，**优先级最高的需求进入早期 increment**。
- **一旦某个 increment 的开发开始，该 increment 的需求即被冻结（frozen）**；但**后续 increment 的需求仍可继续演化**。

> 这条规则是"抗变更"的关键：变更不是被禁止，而是被**推后到下一个 increment**。

## 优点

| 优点 | 说明 |
|---|---|
| 更容易获得客户对**已完成工作**的反馈 | 客户能看到实际运行的东西 |
| 应对客户需求变化的**成本降低** | 变更只影响尚未冻结的 increment |
| 更快交付有用的软件 | 每个 increment 都有价值 |

## 问题

| 问题 | 说明 |
|---|---|
| 需要**更强的配置管理**与**项目协调** | 同时存在多个版本的中间产物 |
| 初始架构必须**灵活且开放** | 能接纳新组件而不破坏已有功能 |
| **系统结构会随增量增加而退化**（degrade） | 局部修改不断破坏整体结构 |

## 增量交付的进阶版本

在增量开发之上，把每个 increment **真正交给客户评论和试用**，就是增量交付。它带来的额外优势：早期且持续的价值交付、更快的 ROI 与现金流、更低的项目风险、更好的反馈回路、更小的"集成冲击"、更好的开发者士气。

对应的代价：架构侵蚀是首要风险、重管理与 CI/CD 开销、范围蔓延、部分可用的挫折感、文档噩梦。
