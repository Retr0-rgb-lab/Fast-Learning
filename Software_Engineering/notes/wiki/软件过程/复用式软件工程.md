# 复用式软件工程 · Reuse-Oriented SE

> **一句话**：基于软件**复用**的集成与配置 —— 系统由**已有的组件、应用系统或 COTS（商用现货）系统**集成而来。**复用现已是构建许多类型业务系统的标准做法。**

课件原文见 [02. Software Processes](<../../raw/02. Software Processes.pdf>)。三种通用模型之一，另两个见 [[瀑布模型]]、[[增量开发]]。

## 什么是复用

被复用的元素可以经过**配置（configured）**以适配用户的需求和行为。

## 三类可复用软件

| 类型 | 英文 | 说明 |
|---|---|---|
| 独立应用系统 | Stand-alone application systems | 被**配置**以适应某个特定环境使用 |
| 对象集合 | Collections of objects | 作为**组件或包**开发，可与 .NET、J2EE 这类框架集成 |
| Web 服务 | Web services | 按**服务标准**开发，可被**远程调用** |

## 复用式软件工程的优缺点

| 优点 | 缺点 |
|---|---|
| 成本与风险降低（**从零开发的软件更少**） | **需求妥协不可避免**，系统可能不满足用户的真实需要 |
| 系统的交付与部署**更快** | **失去对系统演化的控制**（loss of control over system evolution） |

> [!warning] 核心矛盾
> 复用的代价是**把"决定系统该是什么样"的权力交给了被复用的组件**。这与软件最终会持续演化的事实直接冲突 —— 详见 [[软件过程-定义]] 中"演化"的地位。

## 复用在建模层面的体现

复用不是只在代码层发生。**结构模型**在开发中就把"哪些是已有的、可直接复用的构件"标出来，这既是 [[软件过程-四活动]] 中"component selection and design"的设计输入，也是 SRS 结构的组成部分（见 [[软件需求规格说明书]] 中的 *System architecture* 一章要求"highlight 可复用的架构组件"）。
