# 功能需求与非功能需求

> **一句话**：**功能需求**是关于系统**应当提供哪些服务**的陈述；**非功能需求**是对系统**服务或功能的约束**。非功能需求往往比功能需求**更关键**，却常常**更难说清、更难验证**。

课件原文见 [04. Requirements Engineering](<../../raw/04. Requirements Engineering.pdf>)。上位见 [[用户需求与系统需求]]。

## 两者的定义

| | 功能需求 Functional requirements | 非功能需求 Non-functional requirements |
|---|---|---|
| 是什么 | 关于**系统应当提供的服务**的陈述 | 对系统**服务或功能**的**约束** |
| 特殊之处 | **也可以规定系统不应当做什么** | 往往**适用于整个系统**，而不是某个具体功能或服务 |
| 常见性 | 通常落到具体功能上 | 常常涉及**系统的涌现属性（emergent properties）**，因此**适用于系统整体** |
| 重要程度 | — | **可能比功能需求更关键** |

> [!important] 分界线并不总是清晰
> 因为**需求之间不是独立的**，功能与非功能之间的界线**并不总是清楚**。**系统需求应当同时包含这两类。**

## 为什么非功能需求更难处理

1. **难以判断哪个系统组件实现了某个具体的非功能需求** —— 因为它常常是**整体属性**。
2. 非功能需求可能**影响系统的整体架构**，而不是单个组件。
3. 一个非功能需求**可能派生出其他相关的功能需求和/或非功能需求**。

## 可验证的非功能需求 · Verifiable NFR

**可验证的非功能需求 = 使用了某种能被客观测试的度量（measure）的陈述。**

### 为什么要强调"可验证"

非功能需求**难以精确表述**，而**不精确的需求难以验证**。所以"系统应当足够快"这类话没有价值 —— 它既不能实现也不能测试。

### 改写示例

> **不可验证**：在线商店应当**加载迅速**，以免顾客放弃购物车。
> **可验证**：系统应当**在 10,000 并发用户的高峰负载下，对 95% 的请求在 2 秒内加载完任何产品页面**。

两者的差别不在于"意思变了"，而在于**加上了度量、阈值与测量条件**。

> [!warning] 常见错误
> 非功能需求**比**功能需求**更难**验证，不是更容易。正是因为难以精确表述，课件才专门提出"可验证非功能需求"这个概念。若把方向记反，就丢掉了这一节存在的全部意义。

## 指定非功能需求的度量

| 类别 | 覆盖什么 | 典型度量 / 示例目标 |
|---|---|---|
| **性能** Performance | 速度、响应性、吞吐量 | 95 分位响应时间 ≤ 2s；延迟 < 200ms；吞吐 ≥ 1,000 req/s；CPU < 70% |
| **可用性** Availability | 正常运行时间与服务连续性 | 99.9% 可用（≈ 每年停机 8.76h）；99.99%（≈ 52.6min/年）；计划维护窗口 |
| **可靠性** Reliability | 失效频率与一致性 | MTBF ≥ 1,000h；失效率 < 0.1%；缺陷密度 < 1/KLOC |
| **容量** Capacity | 系统能处理的最大量 | 最多 50,000 条记录；5TB 存储；1M 事务/天；10,000 并发会话 |
| **安全性** Security | 防止未授权访问与攻击 | TLS 1.3；AES-256；MFA；严重漏洞 ≤ 24h 修补；5 次失败登录后锁定 |
| **易用性** Usability | 使用的容易程度与可学习性 | 任务完成率 ≥ 90%；任务耗时 ≤ 2min；错误率 < 5%；SUS 分数 ≥ 80 |
| **可访问性** Accessibility | 残障人士的无障碍使用 | WCAG 2.2 AA；对比度 ≥ 4.5:1；可键盘导航；兼容屏幕阅读器 |
| **可测试性** Testability | 验证系统的容易程度 | 自动化测试覆盖 ≥ 80%；测试套件 ≤ 10min 跑完；缺陷检出率 ≥ 95% |
| **合规性** Compliance | 法律、法规、合同义务 | PCI DSS、HIPAA、ISO 27001；审计 100% 通过；日志留存 ≥ 1 年 |
| **效率** Efficiency | 资源消耗 | 内存 ≤ 80%；CPU ≤ 70%；电池续航 ≥ 8h；每事务能耗 ≤ X 焦耳 |
| **本地化** Localization | 语言与地区适配 | 支持 10 种语言；日期/时间/货币格式；翻译覆盖 ≥ 98% |
| **安全性（人身）** Safety | 防止伤害人或环境 | SIL 2/3；危险率 < 10⁻⁹/小时；已验证的失效安全行为 |

## 指定非功能需求的困难

1. **客户难以把目标翻译成可度量的需求**：
   - 某些目标**没有简单的度量**（例如可维护性）
   - **度量与日常体验之间的联系不清楚**
   - **验证成本过高**
2. **难以把功能与非功能需求在需求文档中分开**。

> **高频交易系统示例**（自行补全）：一家交易所的系统，其性能需求是"**99.99% 的所有交易必须在收到市场信号后的 100 微秒内执行完毕**"；可用性需求是"**在交易时段（9:30–16:00）必须有 99.999%（"五个 9"）的正常运行时间**"。这类需求能写出来，正是因为**每个数字都是可测的**。
