# 用户需求与系统需求

> **一句话**：不同类型的利益相关者需要**不同种类的需求**才能理解系统。**用户需求**对客户与用户说需求是什么，**系统需求**对开发者说系统要做什么、做到什么程度。

课件原文见 [04. Requirements Engineering](<../../raw/04. Requirements Engineering.pdf>)。上位见 [[需求工程-定义与过程]]。

## 对照表

| 维度 | 用户需求 User requirements | 系统需求 System requirements |
|---|---|---|
| **读者** | 客户、用户、产品负责人、业务利益相关者 | 开发者、架构师、测试者、需求工程师、项目经理 |
| **定义** | 关于**用户需要系统做什么**、以及任何预期约束的**高层次陈述** | 对系统**必须提供的服务**以及**必须在何种约束下运行**的详细、精确描述 |
| **关注点** | **用户想达成什么** | 系统**必须做什么**、以及**必须做得多好** |
| **主要目的** | 沟通需要、界定宽泛的**范围**、**取得一致** | 指导**设计、实现、测试与验收** |
| **语言** | 自然语言、**用户故事**、场景、简单图示 | **结构化自然语言**、形式模型、表格、技术规格 |
| **细化程度** | 抽象、概括、常常非正式 | 详细、具体、常常结构化且技术性 |
| **可验证性** | 常常**难以直接测试**，可能含糊 | **应当精确、可度量、可测试** |
| **关系** | **表达问题或需求** | 把用户需求**细化、展开为可构建的规格** |

## 对照示例

### 示例一：产品搜索

- **用户需求**：客户应当能够**搜索产品**，以便**快速找到自己需要的东西**。
- **系统需求**：系统应当支持**按产品名、类别和价格区间搜索**；结果应当在**最多 10,000 个产品时 2 秒内**返回；**支持部分匹配**。

### 示例二：待办事项

- **用户需求**：用户应当能够把一个任务**标记为完成**。
- **系统需求**：系统应当允许用户**选择一个任务并把其状态改为 'complete'**；该任务随后应当**显示一个勾号**并**移动到 'Completed' 列表**；该更改应当**立即保存**。

> [!tip] 如何辨别一条需求属于哪一层
> 看它**能不能写出测试用例**。写不出测试的（"快速找到需要的东西"）是用户需求；能写出测试的（"2 秒内返回"）是系统需求。

## 与敏捷的关系

敏捷方法**倾向于不产出详细系统需求**，改用**用户故事**。但这**对业务系统可行，对许多其他系统成问题**。详见 [[用户故事]] 与 [[敏捷宣言与原则]]。
