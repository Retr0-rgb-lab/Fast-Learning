# 软件需求规格说明书 · SRS

> **一句话**：SRS 是**开发者应当实现什么的正式陈述**。它**应当同时包含用户需求和系统需求**，并且**不是设计文档** —— 尽可能说明 **WHAT 而非 HOW**。

课件原文见 [04. Requirements Engineering](<../../raw/04. Requirements Engineering.pdf>)。上位见 [[需求规约]]。

## 定位

- **SRS = 开发者应当实现什么的正式陈述。**
- 文档中的信息**取决于系统类型和所使用的开发过程**。
- **应当同时包含用户需求和系统需求。**
- 需求规约已有**标准**可循：**IEEE Std 830-1998** 与 **ISO/IEC/IEEE 29148**。

> [!warning] SRS 不是什么
> **它不是设计文档。** 尽管实践中需求与设计不可分（见 [[需求规约]]），但 SRS 应当**尽可能说明系统应当做什么，而不是它如何做**。
> 需求规格中的设计元素只有在**显式、有理由、可追踪**时才可接受 —— **悄悄夹带是缺陷**。

## 标准结构

| 章节 | 说明 |
|---|---|
| **前言 Preface** | 定义文档的**预期读者**，并描述**版本历史**，包括创建新版本的理由与每个版本变更的摘要 |
| **引言 Introduction** | 描述**为什么需要**该系统。简要描述其功能，说明**它如何与其他系统协作**，以及**它如何契合**发起该软件的组织的整体业务或战略目标 |
| **术语表 Glossary** | 定义文档中使用的**技术术语**。**不应假定读者的经验或专业水平** |
| **用户需求定义 User requirements definition** | 描述**为用户提供的服务**。**非功能系统需求也应在这一节描述**。可用客户能理解的自然语言、图示或其他记法。应指定必须遵循的产品与过程标准 |
| **系统架构 System architecture** | 给出**预期系统架构的高层概览**，展示**功能在系统模块间的分布**。**被复用的架构组件应高亮标出** |
| **系统需求规格 System requirements specification** | 更详细地描述**功能与非功能需求**。必要时可对非功能需求进一步细化。可定义与其他系统的接口 |
| **系统模型 System models** | 可包含图形化系统模型，展示系统组件之间、系统与环境之间的关系。可能的模型有对象模型、数据流模型、语义数据模型 |
| **系统演化 System evolution** | 描述**系统所基于的基本假设**，以及因硬件演化、用户需求变化等**预期的变更**。这一节对系统设计者有用，可帮助他们**避免那些会限制未来可能变更的设计决策** |
| **附录 Appendices** | 提供与应用相关的**详细、具体信息**，例如硬件与数据库描述。**硬件需求**定义最小与最优配置；**数据库需求**定义数据的逻辑组织及数据间关系 |
| **索引 Index** | 可包含多种索引：普通字母索引、**图索引**、**函数索引**等 |

> [!tip] 两个章节的关系
> *System models*（画出结构与交互）与 *System evolution*（预判未来的变更）都不是可有可无的装饰：前者让需求变得可讨论，后者让设计者**不要做出堵死未来变更的决策**。参见 [[应对变更]]。
