# 重构 · Refactoring

> **一句话**：重构是**在没有任何即时需求时也主动寻找并做出软件改进**。它与"提前为变化做设计"是两种对立的主张。

课件原文见 [03. Agile Software Development](<../../raw/03. Agile Software Development.pdf>)。所属原则见 [[敏捷宣言与原则]]。

## 两种设计观的对立

| 主张 | 内容 |
|---|---|
| **传统智慧 · Design for change** | 值得投入时间与精力**预判变化**，因为这会降低生命周期后期的成本 |
| **XP 的主张** | 改为**持续改进代码**，让变化在必须实现时**更容易实现**。"Design for change" **不值得做**，因为**变化无法被可靠地预判** |

> [!important] 论证结构
> 预判要付出**当下的成本**，而其收益依赖于"预判正确"这个**不可靠的假设**。重构则是**无条件**改善当下结构、从而确定地改善未来。两者取此舍彼。

## 是什么

**寻找可能的软件改进，并做出这些改进 —— 即使当下没有立即的需要。**

典型例子：

- **整理并重命名**属性和方法，使其**更易理解**。
- **用对程序库中方法的调用替换内联代码**（replace inline code with calls to methods included in a program library）。

## 收益与问题

| 收益 | 问题 |
|---|---|
| 提升软件的**可理解性**，并**减少对文档的需求**（因为局部改动本会不断劣化软件结构与可读性） | 重构**有时被推迟**（gets delayed） |
| 变更**更容易做出**，因为代码结构良好、清晰 | 某些改动需要**昂贵的架构级重构** |

> [!warning] 重构被推迟的后果
> 第一条收益明确指出：**局部改动会持续劣化软件结构**。所以"现在没需求"恰恰是不重构的后果，不是重构的理由。

## 在实践列表中的位置

重构是 XP 的一项**实践（practice）**：

> **Refactoring** —— 所有开发者都应在**一旦发现可能的代码改进时立即重构**，持续进行。这保持代码**简单且可维护**。

它同时支撑敏捷原则中的**拥抱变更**与**保持简单**两项。
