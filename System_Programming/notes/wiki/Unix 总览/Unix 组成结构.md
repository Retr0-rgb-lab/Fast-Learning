# Unix 组成结构

> **一句话**：Unix 分成**用户级**和**内核级**两大层。用户级是**Shell + 命令/程序 + 用户库**，内核级是**系统调用接口 + 内核各子模块 + 设备驱动**。用户程序想碰硬件，只有一条路：**通过系统调用陷入内核**。

课件对应 L01 p6–p13。课件原文见 [01-Overview-of-Unix](<../../raw/01-Overview-of-Unix.pdf>)。

## 完整场景：一条命令 `ls` 到底经历了什么

**不预设你写过 C 程序。** 先把要讲的每个角色用一句话交代清楚。

你在终端敲下 `ls` 这个动作，会依次经过四层：

1. **Shell**（命令解释器）读到这行文字 `ls`，把它拆成"程序名 `ls` + 参数"，然后**创建子进程**去执行它
2. **`ls` 程序**开始运行，它需要知道"目录里有哪些文件"
3. **`ls` 调 `open()` / `read()`** 这些**系统调用**
4. **内核**接管，处理这个请求，访问**磁盘**，把结果返回给 `ls`

**四层里，前两层在用户态（unprivileged mode），后两层在内核态（privileged mode）。** 这条分界线是本讲的主轴。

## 系统调用：用户态进内核的唯一门（p9）

这是本讲**最该记住的机制**，也是整个系统编程这门课的主题。

### 课件的定义

> *"Other parts of the Unix system, as well as user programs, request the kernel for various services **through system calls**. A system call is an **entry point into the kernel**, typically packaged as a **function call**, as part of the **OS API**."*
> （Unix 系统的其他部分以及用户程序，都**通过系统调用**向内核请求各种服务。系统调用是**进入内核的入口**，通常包装成一次**函数调用**，作为 **OS API** 的一部分。）

### 一次系统调用的内部流程（p9 原文给的第 1 步）

> *"1. a **software interrupt (trap)** switches the CPU hardware to the kernel"*
> （一次**软件中断（陷阱）**把 CPU 切换到内核）

完整流程按课件的思路是：

```
用户程序
  │  ① 调用 open("file", O_RDONLY)  ← 看起来就是个普通函数调用
  │  ② CPU 执行一条特殊的指令（软件中断 / trap）
  ▼
┌──────────────── 内核态 ────────────────┐
│ ③ 内核保存用户程序的现场（寄存器等）     │
│ ④ 内核根据系统调用号分发到对应处理程序   │
│ ⑤ 执行（碰硬件、碰内核数据结构）         │
│ ⑥ 恢复现场，返回用户态                   │
└───────────────────────────────────────────┘
  ▼
用户程序继续执行，拿到返回值
```

> [!warning] "看起来是函数调用"这件事最容易造成误解
> `open()` 在你代码里写得像普通函数，但**它不是**。
> 普通函数调用是**压栈 + 跳转 + 返回**，硬件层面什么都没变。
> 系统调用是**主动把 CPU 从用户态切到内核态**——这是**特权级切换**，安全机制全靠这一步。
>
> **所以系统调用的开销比普通函数大一个量级。** 这也是 [[Unix 哲学与工具组合]] 里"小工具 + 组合"能赢过"一个大而全的程序"的原因之一：每个小工具都要付启动 + 系统调用的固定成本。

### 用户库 vs 系统调用（p10）

这是初学者最容易混的一层。课件 p10 的图里，`Shell` 和 `Other Libraries` **都在系统调用接口之上**（用户级），只有内核才在下面。

| | 用户库（user-level library） | 系统调用（system call） |
|---|---|---|
| 在哪一层 | **用户态** | **内核态** |
| 例子 | `printf`、`malloc`、`strlen` | `open`、`read`、`write`、`fork` |
| 本质 | **普通函数**，纯用户态代码 | **陷入内核**的特权切换 |
| 谁实现 | 库作者（常是 libc） | **操作系统** |
| 能不能不用 | 能，很多操作可以纯用户态完成 | 不能，它就是进内核的门 |

**关键理解**：一个普通函数内部**也可以**调用系统调用。`printf` 内部最终要调 `write` 才能把字符送到屏幕——那是几十层普通函数调用之后的**一次**系统调用。

> [!tip] 分辨方法
> 头文件是个可靠的线索：`<unistd.h>` / `<fcntl.h>` 里的函数基本是系统调用；`<stdio.h>` 里的多数是用户库函数。**但不是规则**，以实际文档为准。

## Shell：命令解释器（p12）

课件 p12 的定位：

> *"A powerful **command interpreter**（a **user level application**）for Unix — accepts user text commands and carries them out"*
> （一个强大的**命令解释器**（一个**用户级应用**）—— 接受用户的文本命令并执行它们）

**两个容易被忽略的点，课件都点了出来**：

**① Shell 自己就是用户级程序。** 它不享受任何特权，权限和普通程序一样。它之所以能干"读文件、启动程序"这些事，是因为**它调用的都是普通系统调用**——而系统调用对所有用户程序一视同仁地开放（能不能做还受 [[../文件系统结构/权限位与 ls -l|权限位]] 限制）。

**② 一个用户可以有多个 Shell，多个用户也可以各有 Shell 且共存。**

## 设备驱动：硬件无关性的实现（p13、p15）

课件 p13：

> *"Device drivers **encapsulate the hardware**, providing **hardware independency** to other part of the kernel and the user level"*
> （设备驱动**封装硬件**，为内核其他部分和用户级提供**硬件无关性**）

### 这就是"可移植"落地的地方

[[Unix 是什么与由来]] 说 1973 年改写成 C 带来可移植性，但**光有 C 还不够** —— 不同机器的**寄存器地址、中断号、设备控制器都不一样**。

**设备驱动就是把这些差异全部关起来的那一层。**

```
用户程序：「把数据写给磁盘」
   ↓  完全不知道对方是哪块板子
内核文件子系统：调用某个接口
   ↓  完全不知道寄存器长什么样
设备驱动：知道这块板子的寄存器怎么摆
   ↓
硬件
```

**换一块硬件 = 换一个驱动，其他代码一行不动。** 课件 p15 的原话：

> *"One key to the portability is the **device drivers**, specific modules that **encapsulate the hardware details** from the other parts"*

## 命令和工具不在内核里（p11）

课件 p11 有个值得注意的定位：

> *"**Not part of the kernel**, but **a part of the OS**"*
> （**不是内核的一部分**，但是**操作系统的一部分**）

**`ls`、`vi`、`gcc`、`cp`、`mv`、`cat`、`grep` 这些全都不是操作系统提供的功能** —— 它们是**你自己也能写的普通程序**，恰好被标准安装到了系统里。课件 p7 还提到：**标准命令和工具有 250 多个**。

> [!warning] 这个区分的实际意义
> 内核的能力是**很小**的：读写文件、创建进程、管理内存、收发网络。**"打印一个文件"这种功能内核根本没有。**
>
> `cat` 是**用户程序**，它靠 `open` + `read` + `write` 这三个系统调用拼出来的。
> 换成 `head`、`tail`、`sort`、`wc`，**系统调用完全一样，只是用户程序不同**。
>
> 这正是 [[Unix 哲学与工具组合]] 要展开的主题。

## 一句话

> Unix 是分层的：**用户态**（Shell、命令、用户库）和**内核态**（系统调用 + 内核模块 + 驱动）之间，靠一次**软件中断（trap）**跨越；**凡是需要知道硬件细节的地方，都被关在最底层的设备驱动里。**
