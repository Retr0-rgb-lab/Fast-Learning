# Unix 哲学与工具组合

> **一句话**：Unix 不追求"一个程序什么都会做"，而是追求"**每个程序只做一件事、但都能接上别人的输出**"。这套叫 Unix 哲学。于是 `who | sort | lp` 这种看起来复杂的操作，其实只是三个独立小工具被管道串了起来。

课件对应 L01 p5、p11、p12、p19、p20。课件原文见 [01-Overview-of-Unix](<../../raw/01-Overview-of-Unix.pdf>)。

## 完整场景

**先说清楚"组合器"是什么。** Unix 的命令从终端读文字输入、往终端写文字输出。所谓**组合器（compositor）**就是几个特殊的字符，它们**不产生新程序，只是把一个程序的输出接到另一个程序的输入上**：

| 字符 | 名字 | 作用 |
|---|---|---|
| `>` | 重定向输出 | 把输出**覆盖**写入文件 |
| `>>` | 追加 | 把输出**追加**到文件末尾 |
| `<` | 重定向输入 | 从文件读入 |
| `\|` | 管道 pipe | 把左边的输出接到右边的输入 |
| `` ` `` | 反引号 | 把命令的**输出**变成参数 |

**这五个字符不是命令，是 Shell 语法。** 它们的作用全部是**改"哪个文件描述符连到哪儿"** —— 机制见 [[../重定向与管道/I O 重定向与 dup|I/O 重定向与 dup]]。

## 课件的三条陈述（p5）

> *"**Modular design** | A collection of **simple tools, with limited well-defined functions** | **File system** | **Inter-process communication** | The tools can be **easily composed**（via `>`, `>>`, `<`, `|`, `` ` ``）**by a shell to accomplish complex tasks**"*
> （**模块化设计** | 一组**功能有限且定义明确的简单工具** | **文件系统** | **进程间通信** | 这些工具可以由 shell **方便地组合**起来完成复杂任务）

把这句话拆成设计上的三个要素：

| 要素 | 含义 | 缺了会怎样 |
|---|---|---|
| **Modular design** 模块化 | 每个工具**只干一件事** | 变成一个大而全的程序，组合无从谈起 |
| **limited well-defined functions** 功能有限且定义清楚 | 输入输出**有明确契约**（读 stdin、写 stdout） | 没法被下游程序预期 |
| **composed by a shell** 由 shell 组合 | 组合发生在**工具之外** | 每个任务都要重写一遍 |

> [!tip] 第三条是重点：组合能力不在程序里，在程序**外面**
> `who`、`sort`、`lp` 三个程序**彼此完全不知道对方存在**。它们之间没有任何函数调用、没有共享内存、没有协议。
> **唯一的联系是字节流。**
>
> 所以"组合"这件事**根本不需要作者协调** —— 你今天写一个新命令，它立刻就能和 250 个已有命令组合。

## 具体机制一：管道（p20）

课件 p20 把 pipe 称为 **"Unix's pipe is novel"**（Unix 的管道是新颖的），这是它在特性清单里单列一条的原因。

### 定义

> *"A pipe **passes the standard output of one command directly to another command**, to be used as its standard **input**"*
> （管道把一个命令的**标准输出直接传给另一个命令**当作它的**标准输入**）

### 例子一：两步

```
who | sort
```

**逐个拆开**（这是本笔记要示范的"不预设"）：

1. `who` 是一个命令，作用是列出**当前登录的用户**。单独执行它，输出会打印到终端
2. `sort` 是一个命令，作用是**把输入按字典序排序**。单独执行它，如果没给输入，它会等你从键盘敲
3. `who | sort` 意思是：**`sort` 的输入不是键盘，而是 `who` 的输出**

合起来的效果是：列出登录用户，按字典序排好，再打印出来。**两个命令一个都没改。**

### 例子二：三步

```
who | sort | lp
```

再加一个 `lp`（行打印程序，把内容送去打印）。

课件对这条管线的评价是：

> *"Allows **any number** of commands to be connected in a sequence, and **automatically handles the data flow** from one program to the next."*
> （允许**任意多个**命令顺序连接，并**自动处理**从一个程序到下一个的数据流）

> [!warning] "automatically" 是这里的关键
> `sort` 不知道 `who` 的存在，`lp` 不知道 `sort` 的存在。
> **但数据会自己流过去。** 而且中间不需要把任何一步的结果存到磁盘上。
>
> 对比一下"Windows 传统做法"：要先把 `who` 的输出存成文件，再让 `sort` 读那个文件。Unix **省掉了中间介质**。

### 管道与 [[../重定向与管道/管道与进程间通信|管道与进程间通信]] 的区别

**注意区分两个层次**（这是初学者常混的地方）：

| | 本篇讲的"管道特性" | [[../重定向与管道/管道与进程间通信\|管道与进程间通信]] |
|---|---|---|
| 讲的是 | **Shell 语法**：`\|` 这个字符把命令串起来 | **系统调用**：`pipe()` 这个函数创建内核里的管道 |
| 层次 | Shell 负责创建每个进程，然后把 stdout 接到管道 | 内核提供 `int pipe(int fd[2])` |
| 关系 | Shell 的 `\|` **底下就是** `pipe()` | 程序里不用 Shell，也能自己造管道 |

**用 C 写程序时你想要管道，就是调 `pipe()`；在终端敲命令时你用 `|`。** 后者内部会创建前者。

## 具体机制二：输入输出重定向（p19）

课件 p19 列出 Shell 的几项便利特性，第一项就是重定向：

> *"**Redirection of application input and output**, e.g. `ls > myfiles`"*

拆解 `ls > myfiles`：

1. `ls` 单独执行时，把目录内容写到**标准输出**（也就是终端）
2. `>` 的作用：**把标准输出的目标从"终端"改成"文件 `myfiles`"**
3. 于是你看到的是：屏幕不出声，`myfiles` 里出现了刚才那堆内容

**注意 `>` 是覆盖，`>>` 是追加。** 这两个搞混的后果是数据丢失。

> [!tip] 为什么这算"便利特性"而不是"普通功能"
> `ls` 这个程序**自己完全不知道**有重定向这回事。它以为自己在往"标准输出"写。
> **是 Shell 在创建它的时候，把它的标准输出接到了别的地方。**
>
> 这就是"组合能力在程序外面"的又一处体现。

## 具体机制三：shell script（p19）

课件 p19 还提到一项：

> *"Executing a sequence of commands stored in a text file, called a '**shell script**,' allowing us to **build our own commands**, which may be **parameterized**"*
> （执行一个存放在文本文件里的命令序列，称为 **shell script**，让我们**构建自己的命令**，而且这些命令**可以带参数**）

**这就把组合从"临时手打"变成了"可复用资产"。**

- 手打 `who | sort | lp` 是一次性的
- 写进 `report.sh` 存起来，明天还能用
- 课件还提了 **parameterized**（带参数）—— 意味着它接近一个编程语言

**这正是"词汇 + 语法"这个比喻的落点**，见下一节。

## "词汇 + 语法"：Unix 为何能表达几乎任意功能（p11）

课件 p11 的原话是本节的题眼：

> *"A large set of tools for various basic user level functions | **A vocabulary and a grammar**, to combine basic user level functions to **nearly arbitrary sophisticated functions**"*
> （一大堆做基本用户级功能的工具 | 一个**词汇和语法**，用来把基本用户级功能组合成**几乎任意复杂的功能**）

### 这个比喻怎么落地

| 语言学概念 | Unix 里对应什么 |
|---|---|
| **词汇 vocabulary** | 250 多个标准命令与工具，每个只做一件事 |
| **语法 grammar** | `>` `>>` `<` `\|` `` ` `` 和 `;`、`&&`、`\|\|` 这几个连接符 |
| **句子** | 一条命令行 |
| **文章** | shell script |

**250 个词 + 5 个语法规则 = 几乎任意复杂的功能。** 这不是修辞，这是字面意义上的组合爆炸。

### 为什么这个设计是划算的

对比两种思路：

| | "大而全"程序 | Unix 的"小工具 + 组合" |
|---|---|---|
| 要实现新功能 | 在大程序里改代码、重新编译、重新发布 | **用已有命令拼**一个几行的 shell script |
| 测试 | 整个程序的测试 | 每个命令各自已测过 |
| 复用 | 很难复用别人内部的功能 | **天然可复用**（只要输入输出契约清楚） |
| 成本 | 随功能数增长 | 随命令数增长，组合是免费的 |

> [!warning] 小工具 + 组合有真实代价，别把它当银弹
> 课件没有讲，但这是实际的取舍：
> - **每个小进程都要付启动开销**，而系统调用本身就很贵（见 [[Unix 组成结构]] 里的 trap 成本）
> - **数据要在用户态和内核态之间反复搬运**，中间可能落盘
> - 大量 `grep` 串起来扫大文件，**其实不如写一个专用程序**
>
> 所以现代实践里两者混用：粗活（找文件、筛文本）用管道串命令，**热路径**上的活写专用程序。
> 这个"Unix 哲学"并没有被淘汰，只是它的适用范围被更精确地划出来了。

## 命令不属内核，但属于 OS（p11）

课件 p11 有一句容易被跳过的定位，讲 [[Unix 组成结构]] 时提过，这里补上它的意义：

> *"**Not part of the kernel**, but **a part of the OS**"*

**"小工具"是用户自己也能写的程序。** `cat` 的全部功能就是 `open` + `read` + `write` 的循环。

**这才是 Unix 哲学能被任何人扩展的原因** —— 你写一个程序，就自动获得了和 250 个标准命令组合的能力，**不需要任何人批准、不需要改内核、不需要重新设计任何协议**。

## 一句话

> Unix 的能力不集中在任何单个程序里，而是**分散在 250 多个"只做一件事"的小工具 + 5 个组合器**上；所以 `who | sort | lp` 能完成的事，比任何一个程序单独能做的都多。
