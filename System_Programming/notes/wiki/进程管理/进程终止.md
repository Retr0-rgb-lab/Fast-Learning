# 进程终止

> **一句话**：进程结束时分两条路 —— **正常终止**有四种触发方式（`return` from main、隐式 return、调 `exit()`、调 `_exit()`），**异常终止**有两种（调 `abort()`、被致命信号杀死）。关键区别：**正常终止会跑用户注册的清理钩子，异常终止不会。**

课件对应 L02 p40–p42。课件原文见 [02-Unix-Processes](<../../raw/02-Unix-Processes.pdf>)。

## 完整场景：进程死了，内核要做什么

进程终止**不是"消失"，而是一套固定动作**。课件 p40 列出了内核要做的事：

> *"Upon termination of a process, the OS **de-allocates the resources** held by the process, **updates the appropriate statistics**, and **notifies other processes**, specifically these include:"*
> （进程终止时，操作系统会**释放该进程持有的资源**、**更新相应的统计数据**，并**通知其他进程**，具体包括：）

课件列出的四项：

| # | 内核要做的事 |
|---|---|
| 1 | *"**cancel pending timers and signals**"* 取消待处理的定时器和信号 |
| 2 | *"**release virtual memory spaces**"* 释放虚拟内存空间 |
| 3 | *"**release locks, closing open files**"* 释放锁、关闭打开的文件 |
| 4 | *"**notifying the parent in response to a `wait`**"* 在响应 `wait` 时通知父进程 |

**第 4 条正是 [[wait 等待子进程|wait]] 那一篇的接口** —— 父进程挂起在 `wait` 上，内核在这里把它唤醒并交出退出状态。

> [!tip] 这张表解释了 Unix 程序"退出后什么都会清干净"的来源
> 第 2、3 条说明：**打开的文件会自动关闭、锁会自动释放、内存会自动回收。**
> 所以 Unix 里没有"我忘了 close 文件，句柄泄漏"这种常见负担 —— 进程一死，系统兜底。

## 一、正常终止（p41）

课件 p41 给出**四条**路径：

> *"A **normal termination** occurs if there was:"*
> （出现以下情况则发生**正常终止**：）

| # | 触发方式 | 说明 |
|---|---|---|
| 1 | ***A return from `main`*** | `main` 里 `return` |
| 2 | ***An implicit return from `main`*** | **隐式** return —— `main` 末尾没写 `return` 就到头 |
| 3 | ***A call to the C function `exit`*** | 调 C 库函数 `exit()` |
| 4 | ***A call to the `_exit` system call*** | 调**系统调用** `_exit()` |

### 前两条其实是同一条

**第 2 条"隐式 return"就是第 1 条的特例**：`main` 走到末尾没有 `return`，编译器会**自动补一个 `return 0`**。所以这两条本质上是同一件事。

### 第 3、4 条的区别：这一层很关键

课件给了一句非常重要的区分：

> *"`exit` calls **user-defined exit handlers** and may provide **additional cleanup** before it invokes the `_exit` system call."*
> （`exit` 会**调用用户定义的退出处理器**，并可能在调用 `_exit` 系统调用**之前**做额外的清理。）

**用图表示出这条调用链：**

```
你的代码
   │
   │ return from main（显式或隐式）
   ▼
   ┌──────────────────────────┐
   │  exit()                  │  ← C 库函数
   │  ┌────────────────────┐  │
   │  │ 跑 atexit() 处理器  │  │  ← 用户注册的清理钩子
   │  │ + 冲刷 stdio 缓冲区 │  │
   │  └────────────────────┘  │
   │  额外清理                │
   └──────────┬───────────────┘
              │ 调用
              ▼
   ┌──────────────────────────┐
   │  _exit()                 │  ← 系统调用
   │  直接进内核，不跑任何     │
   │  用户态钩子               │
   └──────────┬───────────────┘
              ▼
           内核清理
   （释放内存、关文件、通知父进程）
```

**关键**：**`exit` 是用户态的 C 库函数，`_exit` 是系统调用。** 前者会做一整套用户态善后，后者直接交给内核。

> [!warning] 这条区别在 `fork` 之后是致命的
> 回顾 [[../进程管理/fork 创建进程|fork]]：**`fork` 会复制父进程的全部内存**，包括 `stdio` 缓冲区里**已经写入但还没冲刷**的内容。
>
> 如果子进程调 `exit()`：
> 1. 它会冲刷缓冲区 —— **但那是父进程那份内容的副本**
> 2. 于是**父进程本来要输出一次的东西，被输出了两次**
>
> **所以 `fork` 之后、子进程 `exec` 之前的出口必须是 `_exit()`。**
>
> 课件 L02 **提到了 `exit` 和 `_exit` 的区别（p41），但没有把这条规则讲出来**。这条推导见 [[../进程管理/wait 等待子进程|wait 等待子进程]] 第五节的完整示例。

## 二、异常终止（p42）

课件 p42 的原话：

> *"A process can terminate abnormally by:"*
> （进程可以以下列方式异常终止：）

| # | 触发方式 | 说明 |
|---|---|---|
| 1 | *"calling `abort`, causing the **`SIGABRT`** signal to be sent to the calling process"* | 调 `abort()`，向自己发 **SIGABRT** 信号 |
| 2 | *"processing a signal that **causes termination**"* | 处理了**导致终止的信号** |

**两种方式在课件里被写成两条，但本质上是一条**：`abort()` 是**通过给自己发 SIGABRT 来实现的**。

### 与正常终止的三个区别（p42）

课件 p42 最后两句：

> *"A **code dump** may be produced."*
> （可能会产生**内存转储 / core dump**。）

> *"**User-installed exit handlers will not be called** upon abnormal termination."*
> （异常终止时，**用户安装的退出处理器不会被调用**。）

| | 正常终止 | 异常终止 |
|---|---|---|
| 触发 | `return` / `exit` / `_exit` | `abort` / 致命信号 |
| **用户装的 atexit 钩子** | ✅ **会跑** | ❌ **不跑** |
| 内存转储 | 通常没有 | **可能有**（core dump） |
| 退出码语义 | 携带状态值（`exit(n)` 的 `n`） | 由**信号编号**决定 |

> [!warning] "钩子不跑"是崩溃排查时最让人头疼的一点
> 你给程序注册了清理逻辑（关文件、还锁、发告别消息），一旦它**段错误崩了**：
> - **那些钩子一个都不会执行**
> - 打开的文件**没被程序关**（靠内核兜底，见本文开头第 3 条）
> - 想查为什么崩，只能靠 **core dump**
>
> 这就是为什么"关键收尾不能只依赖 `atexit`"。

## 三、退出状态：父进程能看到什么

[[wait 等待子进程|wait]] 里那个 `int *stat`，装的就是这里说的**退出状态**。它怎么编码，取决于走的是哪条路：

| 终止方式 | `status` 里装的是什么 | 提取它的宏 |
|---|---|---|
| `exit(n)` / `return n` | **退出码 `n`** | `WEXITSTATUS(status)` |
| 被 `SIGABRT` 等信号杀死 | **信号编号** | `WIFSIGNALED(status)` / `WTERMSIG(status)` |

所以父进程拿到 `status` 后的判断顺序是：

```c
int status;
pid_t pid = wait(&status);

if (WIFEXITED(status)) {
        printf("正常退出，退出码 = %d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
        printf("被信号 %d 杀死\n", WTERMSIG(status));
}
```

> [!note] `WIFEXITED` 等宏不是课件给的
> 课件 p29/p30/p31 只讲了 `wait(&stat)` 和 `status` 存退出状态，**没有列出这些宏**。
> 上表里的宏名是 Unix 上读取 `status` 的标准接口。
> **本篇标注清楚这一点**，不把补充当成课件原文。

## 一句话

> 正常终止有四条路径（`return` from `main`、隐式 `return`、`exit()`、`_exit()`），**`exit` 会跑用户钩子再调 `_exit`**；异常终止只有一种本质（致命信号，`abort` 是自己给自己发 SIGABRT），**不跑用户钩子、可能有 core dump**。内核无论走哪条路都会释放资源并通知父进程。
