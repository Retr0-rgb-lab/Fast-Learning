# 后台进程与守护进程

> **一句话**：命令末尾加 **`&`** 让它在后台跑、终端立刻还给你。但后台进程会**跟着终端一起死**。真正要长生的进程叫 **daemon（守护进程）**，它的标准做法是 **fork 两次、让中间那个进程退出、自己被 init 收养**。

课件对应 L02 p43–p45。课件原文见 [02-Unix-Processes](<../../raw/02-Unix-Processes.pdf>)。

## 完整场景

先回顾 Shell 的运行模式（课件 p43 明确回顾了）：

> *"Recall that the shell is a command interpreter which: **Prompts for commands**; **Reads the commands from standard input**, **forks children to execute the commands**, and **waits for the children to finish**. A user can **terminate execution of a command by `ctrl-c`**."*
> （回顾一下：shell 是一个命令解释器，它**提示输入命令**、**从标准输入读命令**、**fork 子进程去执行**、**等子进程结束**。用户可以用 **`ctrl-c`** 终止一个命令的执行。）

**这个循环就是本篇的出发点。**

## 一、后台进程：加一个 `&`（p43）

课件 p43：

> *"Most shells interpret a command line ending with **`&`** as one that should be executed in the **background**."*
> （多数 shell 把**以 `&` 结尾**的命令行解释为**在后台执行**。）

### 具体是什么变了

| | 前台（默认） | 后台（加 `&`） |
|---|---|---|
| Shell 行为 | **fork 后 `wait`**，自己挂起 | **fork 后不 `wait`**，**立刻回到提示符** |
| 你的感觉 | 命令跑完才能敲下一条 | 敲 `&` 之后**立刻可以接着敲** |
| 输出去哪 | 打到终端（你能看见） | **仍打终端**，但和你的输入混在一起 |
| 能用 `ctrl-c` 停吗 | ✅ **能** | ⚠️ `ctrl-c` 发给**前台进程组**，后台的**收不到** |

> [!tip] `ctrl-c` 为什么停不了后台进程
> `ctrl-c` 实际上不是"停止进程"，而是**向终端的前台进程组发送 SIGINT 信号**。
> 后台进程**不属于前台进程组**，所以收不到这个信号。
>
> 课件 p43 只说"A user can terminate execution of a command by `ctrl-c`"，**没有解释为什么停不了后台的**。上面这段是根据"信号发给进程组"这一机制补的 —— **课件 L02 没有讲信号与进程组**，属于背景补充。

### 后台进程的两个隐患（这是本篇的关键转折）

| 隐患 | 原因 |
|---|---|
| **跟着终端一起死** | 后台进程是**这个 shell 的孩子**。shell 一退出（或关掉终端窗口导致 SIGHUP），孩子就收到挂断信号 |
| **没人在乎它死活** | 它不在前台，**退出码没人 `wait` 取** —— 这正是 [[wait 等待子进程|wait]] 那一节说的"孤儿进程 / 退出状态丢失" |

**所以后台进程适合"跑一会儿的活"，不适合"要一直活着的服务"。** 后者需要下一节的做法。

## 二、daemon 是什么（p44）

### 课件的定义

> *"A **daemon** is a **background process** that normally **runs indefinitely**（have an **infinite loop**）."*
> （**daemon 是一种后台进程**，通常**无限期运行**（有一个**无限循环**）。）

**"infinite loop"（无限循环）是 daemon 的结构特征** —— 它做完一轮活就回到循环开头等下一轮，而不是做完就退出。

### Unix 靠大量 daemon 做日常杂事（p44 原文清单）

| daemon | 职责 |
|---|---|
| **pageout daemon** | 处理**分页 / 页面置换**（paging） |
| **in.rlogind** | 处理**远程登录请求** |
| **web server daemon** | 接收 **HTTP 连接请求** |
| **ftp daemon / mail daemon** | 文件传输 / 邮件 |

> [!tip] 这张清单说明了一件事
> 你在终端里敲的任何一条命令，背后**可能有某个 daemon 在替你干活**。
> 比如你敲 `ssh` 远程登录，真正接受连接的是 `in.rlogind` —— 它一直在等（无限循环），你一连上它就 fork 一个子进程去伺候那个会话。

### 课件的提问（p44 结尾）

> *"**How does a daemon ...**"*
> （**daemon 是怎么……的**）

原文在此处被截断（PDF 排版）。**课件用这个问题引出下一页的实现代码。**

## 三、daemon 怎么实现：两级 fork（p45）

课件 p45 给了一段完整代码，**核心是三次 fork 的结构**。先把骨架画出来，再看细节。

### 骨架

```
shell 执行某个程序
   │
   │  fork #1
   ▼
 进程 A  ────────────────────────▶ 退出
   │                                ↑
   │  fork #2                       │
   ▼                                │
 进程 B（孤儿）────────────────────▶ 退出
   │                                ↑
   │  现在 B 是孤儿，被 init 收养      │
   ▼
 进程 C  ← 真正的 daemon，开始无限循环
   │
   └─▶ 一直活着，不退出
```

**为什么是两次 fork 而不是一次？** 逐层看：

### 为什么第一次 fork

```
shell  ──fork──▶  进程 A
```

**目的**：让 shell 有孩子可以 `wait`。A 立刻退出，shell 收掉它、**回到提示符**。

**这样 daemon（也就是后来的 C）就成了 shell 的孙子，PPID 指向 PID 1 而不是 shell。**

### 为什么第二次 fork（p45 代码里的关键一行）

```
进程 A  ──fork──▶  进程 B
   │
   └─ A 立刻 exit(0)
        ↓
进程 B 的父进程（A）已经死了
        ↓
★ 进程 B 成为孤儿进程，被 init 收养 ★
        ↓
进程 B 再 fork ──▶  进程 C
   │
   └─ B 立刻 exit(0)
        ↓
进程 C 的父进程（B）已经死了
        ↓
★ 进程 C 也成为孤儿，被 init 收养 ★
```

**第二次 fork 的作用是让 B 变成孤儿，从而 C 也变成孤儿。** 为什么要绕这一圈？

> [!warning] 关键收益：C 永远不会是"会话首进程"，因此拿不到控制终端
> 这就牵涉到 **会话（session）** 和**控制终端**的概念：
>
> **一个会话的首进程（session leader）会获得控制终端。** 而如果 daemon 是直接被 shell fork 出来的（第一次 fork 的产物），它**有可能成为会话首进程、从而持有终端**。
>
> 一旦持有终端，终端关闭时会给它发 SIGHUP，**它就死了**。
>
> **绕两次 fork 之后，C 的 PPID 是 1、它自己不是会话首进程、不持有任何终端** —— 于是终端关掉也不影响它。
>
> **注意**：这套"两次 fork + setsid + 脱离所有 fd"的写法是 **BSD 传统 daemon 化流程**，也是课件 p45 代码采用的结构。
> **课件 L02 没有讲会话（session）、控制终端、SIGHUP 这些概念**，上面这段是根据代码结构补的机制解释 —— **标记为背景补充，不是课件原文**。

### p45 代码的骨架

课件 p45 的代码包含 `#include <syslog.h>` 和 `MAX_I 100`，说明它是一个**完整的守护服务程序**（会写 syslog）。核心结构（**已简化，具体代码以课件为准**）：

```c
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <syslog.h>
#include <string.h>

#define MAX_I 100

void main(void){
        pid_t pid, sid;
        FILE *p_output;
        int i = 0;

        pid = fork();
        if (pid < 0)  exit(EXIT_FAILURE);   /* fork 失败 */
        if (pid > 0)  exit(EXIT_SUCCESS);   /* ★ 父进程立刻退出 ★ */

        /* 到这里已经是第一次 fork 的子进程 */

        pid = fork();
        if (pid < 0)  exit(EXIT_FAILURE);   /* 第二次 fork 失败 */
        if (pid > 0)  exit(EXIT_SUCCESS);   /* ★ 中间进程立刻退出 ★ */

        /* 到这里已经是第二次 fork 的子进程 = 真正的 daemon */
        /* PPID 现在是 1（被 init 收养）*/

        /* … 接下来脱离终端、设置工作目录、进入无限循环 … */
}
```

**三个分支的含义（对照 [[../进程管理/fork 创建进程|fork]] 的返回值）：**

| 判据 | 我是谁 | 动作 |
|---|---|---|
| `pid < 0` | fork 失败 | `exit(EXIT_FAILURE)` |
| `pid > 0` | **父进程** | `exit(EXIT_SUCCESS)` ← **两次 fork 都是这样** |
| `pid == 0` | **子进程** | 继续往下走 |

> [!warning] 两次 fork 的分支完全一样，这个"重复"就是重点
> 很多人看到两段几乎相同的代码会困惑。**它们的作用是递进的：**
> - 第一次：脱离 **shell**（让 shell 能 `wait` 到、回到提示符）
> - 第二次：脱离**会话首进程的身份**（拿到控制终端的风险）
>
> 第二次的代码看着"多余"，但去掉它，daemon 就可能在某些启动路径上持有终端。

## 四、两种"长生"的对比

| | 后台进程（`&`） | **daemon** |
|---|---|---|
| 怎么启动 | 命令末尾加 `&` | fork 两次脱离 |
| Shell 要不要等它 | **不等** | **等**（fork 出中间进程就退出） |
| PPID | **shell** | **1（init）** |
| 终端关掉会死吗 | ⚠️ **会**（收 SIGHUP） | ✅ **不会** |
| 结构 | 跑完就结束 | **无限循环** |
| 退出码有人取吗 | ❌ 没有 | 由 init 收 |
| 典型用途 | 跑个长一点的编译、下载 | **常驻服务**：sshd、httpd、crond |

> [!tip] 一个判断口诀
> **"要不要在关掉终端后继续跑"** —— 要，就得是 daemon；不要，`&` 够了。
>
> 在本机跑训练任务时这是个真问题：`nohup python train.py &` 里的 **`nohup`** 就是"忽略 SIGHUP"，属于**后台进程 + 抗挂断**的组合，仍然不是完整意义的 daemon。

> *"What is a process called **if it never die**?"*
> （**永不死亡**的进程叫什么？）

**答案：daemon（守护进程）。** 见本篇第二节。

## 一句话

> **后台进程**是命令加 `&`（Shell 不 `wait`、立刻返回），但**会跟着终端一起死**；**daemon** 是无限循环的后台进程，用 **fork 两次**让中间进程退出、自己被 **init 收养**，从而**不持有终端、关掉终端也不死**。
