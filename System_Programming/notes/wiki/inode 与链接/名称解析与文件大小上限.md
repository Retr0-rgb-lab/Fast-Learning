# 名称解析与文件大小上限

> **一句话**：**name resolution** 是把路径名转成 i-number 的过程 —— 逐级在目录文件里查名字。**文件大小上限**则由 inode 里的**多级间接指针**决定：12 个直接指针 → 单间接 → 双间接 → 三间接，一层层把"能寻址多少块"乘上去。

课件对应 L03 p33–p34。课件原文见 [03-Unix-File-System](<../../raw/03-Unix-File-System.pdf>)。

## 一、名称解析（p33）

### 课件的定义

> *"**Name resolution** is a function to **convert a pathname to an i-node number**."*
> （**名称解析**是一个**把路径名转换成 i-node 号**的函数。）

> *"When a program references a file by pathname, OS **traverses the file system tree** to find the **filename and the i-number** in the appropriate directory. **Once it has the i-number, the OS can determine**..."*
> （当程序用路径名引用一个文件时，操作系统**遍历文件系统树**，在相应的目录里找到**文件名和 i-number**。**一旦拿到 i-number，操作系统就能确定**……）

**定义极其简洁：路径名 → i-number。** 这一步做完，就从"人能读的名字"跨到了"内核能用的编号"，后面所有操作都只认 i-number。

### 完整走一遍

用这棵树：

```
/                     ← 根目录
└── dirA
    ├── My1.dat       (i-number 230)
    └── dirB
        └── My1.dat   (i-number 231)   ← 同名但不同文件
```

**访问 `/dirA/dirB/My1.dat` 的解析过程：**

| 步 | 在哪查 | 找什么名字 | 得到什么 |
|---|---|---|---|
| ① | **根目录** `/` 的文件里 | `dirA` | i-number（假设 120） |
| ② | 用 120 找到 **dirA 的 inode** → 知道它的数据块在哪 | — | 拿到 dirA 的目录内容 |
| ③ | **dirA 的目录文件**里 | `dirB` | i-number（假设 121） |
| ④ | 用 121 找到 **dirB 的 inode** → 知道它的数据块在哪 | — | 拿到 dirB 的目录内容 |
| ⑤ | **dirB 的目录文件**里 | `My1.dat` | **i-number 231** ← 解析完成 |

**然后**（这一步不属于 name resolution）：
```
拿 i-number 231 → 查 i-node 表第 231 项 → 读到 inode → 按 inode 里的指针读数据块
```

> [!tip] 第 ①③⑤ 步都是"查目录表"，第 ②④ 步是"读 inode 拿目录内容的块号"
> 看出规律了吗？**"查名字"和"取元信息"是交替出现的。**
>
> 每往下一层都要：
> 1. 在**当前目录**里按名字查 → 得到 i-number
> 2. 用 i-number **换出下一个目录/文件**（对目录来说是"下一个目录"，对普通文件来说是"内容"）

### 相对路径的 name resolution

**唯一的区别是第 ① 步从哪开始**：

| | 第 ① 步从哪查 |
|---|---|
| **绝对路径** `/dirA/dirB/My1.dat` | 从**根目录 `/`** |
| **相对路径** `dirB/My1.dat` | 从 **cwd** |

后面完全一样。cwd 见 [[../文件系统结构/当前工作目录|当前工作目录]]。

> [!warning] 相对路径的风险就在第 ① 步
> 同一条 `dirB/My1.dat` 命令，**你在不同目录敲，它去不同地方查名字**。
> 这就是为什么脚本里应该用绝对路径 —— 见 [[../文件系统结构/层次结构与路径名|层次结构与路径名]] 第四节的讨论。

### 符号链接要多走一轮

从 [[硬链接与符号链接]] 得知，符号链接的内容是一串路径。所以解析时**会多出一步**：

```
读到 My1SymLink.dat  →  i-number 250（一个普通文件）
                              │
                        读它的内容
                              ▼
                      "./My1.dat"  ← 一串路径
                              │
                        ★ 再做一次完整的 name resolution ★
                              ▼
                      找到真正的 i-number 230
```

**这就是"符号链接移动后会断"的机制** —— 第二轮解析找不到那个路径了。

> [!tip] 一个推论：符号链接可以构成环
> 因为符号链接的内容本身会被解析，**如果 A 指向 B、B 指向 A，就会无限循环**。内核有专门的检测（一般限制层数）来处理。
>
> ⚠️ **课件 L03 没有讲符号链接成环**，这是根据 name resolution 机制推出来的，**背景补充**。

## 二、文件能有多大：多级间接寻址（p34）

### 问题的起点

[[inode 与目录文件]] 说 inode 里记着"数据块位置"。**那么问题来了：inode 本身是固定大小的，它能记多少个数据块？**

**数据在磁盘上按"块"存储**（课件 p34 用的是 **8 KB** 的块）。所以：

> **能存多大文件 = 能寻址多少块 × 每块多大**

**限制来自 inode 里那个指针字段的个数。**

### 三层间接指针（p34 原文）

课件 p34 的原话：

> *"**12 direct pointers** can point to **12 × 8KB = 96KB** of file content."*
> （**12 个直接指针**可以指向 **12 × 8KB = 96KB** 的文件内容。）

> *"A **single indirect pointer** points to **a block of direct pointers**. A block can contain **8KB/4bytes = 2K pointers = 2048 pointers**. **2048 direct pointers** can point to **2048 × 8KB = 16MB** of file content."*
> （一个**单间接指针**指向**一个存放直接指针的块**。一个块能装 **8KB/4 字节 = 2K 个指针 = 2048 个指针**。**2048 个直接指针**能指向 **2048 × 8KB = 16MB** 的文件内容。）

> *"A **double indirect pointer** points to 2048 single..."*（后续被截断）

### 逐层拆解

**① 直接指针（direct pointer）**

指针**直接指向数据块**。

- **个数**：**12 个**（inode 里直接写死）
- **能寻址**：$12 \times 8\text{KB} = \mathbf{96\text{KB}}$

**② 单间接指针（single indirect）**

指针**不指向数据块，而是指向"一个装满数据块号的块"** —— 这一层多绕了一次，所以叫"间接"。

- **间接层里能装多少个指针？**
  $$\frac{8\text{KB}}{4\text{字节}} = \frac{8192}{4} = 2048\ \text{个指针}$$
  （**每个指针 4 字节**）
- **能寻址**：$2048 \times 8\text{KB} = \mathbf{16\text{ MB}}$

**③ 双间接指针（double indirect）**

指针指向"装满单间接块号的块" —— **间接了两层**。

- **能寻址**：$2048 \times 2048 \times 8\text{KB} = \mathbf{32\ \text{GB}}$

**④ 三间接指针（triple indirect）**

- **能寻址**：$2048^3 \times 8\text{KB} = \mathbf{64\ \text{TB}}$

### 一张表看全

| 层级 | 指针指向 | 寻址上限 | 相比上一级 |
|---|---|---|---|
| **直接** | 数据块 | **96 KB** | — |
| **单间接** | 装数据块号的块 | **16 MB** | ×约 170 |
| **双间接** | 装单间接块号的块 | **32 GB** | ×2048 |
| **三间接** | 装双间接块号的块 | **64 TB** | ×2048 |

**总上限**（三层全用满时）：

$$
96\text{KB} + 16\text{MB} + 32\text{GB} + 64\text{TB} \approx \mathbf{64\ \text{TB}}$$

> [!tip] 为什么真实文件系统能超过 64 TB
> 上面这套 12 指针 + 三层间接是**课件 p34 用的经典模型**，很多教学材料都用它。
>
> **真实的文件系统**（如 Linux 的 ext4）用了更多技巧：比如 ext4 把间接块数量也存进 i-block 数组、允许**稀疏文件**（空洞不算块）、以及**extent**（区间）机制 —— 所以实际上限远大于此。
>
> **课件 L03 只讲了 p34 那一种模型**，本篇按课件照录，不展开其他设计。

### 为什么小文件不占额外空间

**这套设计最巧妙的地方**：一个小文件（比如 100 字节）**只需要直接指针**。

```
文件只有 10 KB
      ↓
只用 12 个直接指针里的 1 个（甚至不到 1 个块）
      ↓
★ 不需要任何间接块 ★   ← 省下的空间就是"小文件多起来"时省下的空间
```

> [!warning] 这个设计有一个代价
> 随机访问一个大文件，要**多次间接跳转**：先读单间接块 → 拿到数据块号 → 再读数据块。**层数越深，访问越慢。**
>
> 所以"文件上限"和"访问速度"在经典 Unix 设计里是**互相拉扯**的。

## 三、name resolution 与多级寻址的分工

把两件事分清楚，它们解决的是**完全不同的两个问题**：

| | **name resolution**（p33） | **多级间接寻址**（p34） |
|---|---|---|
| **问题** | 这个文件**是谁**？ | 文件的**内容在哪**？ |
| **输入** | 路径名 | i-number |
| **输出** | i-number | 数据块 |
| **手段** | **逐级查目录表** | **按指针跳** |
| **在哪做** | 目录文件（名字 ↔ i-number） | inode（块号指针） |
| **失败的样子** | "No such file or directory" | 越界/指针无效 |

**完整的一次文件访问，两件事都要做：**

```
open("/dirA/dirB/My1.dat")
   │
   ├─ name resolution（p33）：路径名 → i-number 231
   │     逐级查目录表
   │
   └─ 多级间接寻址（p34）：i-number 231 → 数据块
         查 i-node 表 → 读 inode → 按直接/间接指针跳 → 拿到内容
```

**第一步答"你是谁"，第二步答"你的内容在哪"。** 这正是 [[inode 与目录文件]] 那张链路图的第 ① 步和第 ④ 步。

## 一句话

> **name resolution** 把路径名逐级查成 i-number（查目录表，每层交替"查名字"和"读 inode"），**符号链接要再做一轮**；**文件大小上限**来自 inode 里的 **12 直接指针 → 单间接 → 双间接 → 三间接**，按 $8\text{KB}$/块、$4$ 字节/指针算出 **96 KB / 16 MB / 32 GB / 64 TB** 四级。
