# inode 与目录文件

> **一句话**：**文件名不存在 inode 里。** 目录文件本身是一张 **"名字 → i-number"** 的表，inode 里存的是**类型、权限、大小、数据块位置**这些元信息。所以**两个不同的目录可以有两个同名文件**，而**硬链接则是两个名字指向同一个 inode**。

课件对应 L03 p15–p26。课件原文见 [03-Unix-File-System](<../../raw/03-Unix-File-System.pdf>)。

> ![[目录、硬链接、inode 与数据块关系图.jpg]]
>
> 这张图就是本篇全部内容的总览：**目录**是名字与 i-number 的映射表，**inode** 里**没有文件名**、只存元信息和数据块位置，硬链接是多个名字指向同一个 inode。

## 完整场景：为什么文件名要单独放

**先看课件 p15 提出的问题。** 目录树上每个节点都是文件，每个文件都有一串名字。那么最自然的设计是：**把文件名和文件的其他信息放在一起存进 inode。**

**Unix 没有这么做。** 课件 p16 直接把这个问题摆出来：

> *"**Where is the file name stored?**"*
> （**文件名存在哪里？**）

**这个问题不是学术兴趣，它决定了 Unix 文件系统的整个形态。** 答案有两个后果：

| 后果 | 说明 |
|---|---|
| **同名文件可以合法存在** | `/dirA/My1.dat` 和 `/dirA/dirB/My1.dat` 是两个不同文件，见 [[层次结构与路径名|层次结构与路径名]] |
| **一个文件可以有多个名字** | 这就是[[硬链接与符号链接|硬链接]] |

## 一、inode 里存什么、不存什么（p15、p16）

课件 p15 的原话：

> *"Information about a filesystem structure is stored **both on disk and main memory**. Unix uses a **logical structure called i-node** to store the information about a file **on disk** — **each file in a file system is represented by an i-node**."*
> （文件系统结构的信息**既存在磁盘上、也存在主存里**。Unix 用一个叫 **i-node** 的**逻辑结构**来存储文件在**磁盘上**的信息 —— 文件系统里的**每个文件都由一个 i-node 表示**。）

**"每个文件"包括目录** —— 这一点很关键，下面会用到。

### inode 里有什么、没有什么

课件 p16 之后的几页（p17–p24）就是逐步揭示 inode 的内容。按本笔记整理成两类：

| 类别 | 内容 |
|---|---|
| **有** | 文件**类型**（普通/目录/设备…）、**权限**、**所有者**（UID/GID）、**文件大小**、**时间戳**、**数据块位置**（本篇第四节的多级间接指针）、**硬链接计数** |
| **❌ 没有** | **文件名** ← 这就是 p16 那个问题的答案 |

> [!tip] 那张关系图里的一句话最关键
> 图上标的是：**`inode 不保存文件名`**。
>
> 把这句话和"每个文件有一个 inode"合起来：
> ```
> 文件 = ① 名字（在某个目录里）
>      + ② inode（内核用来识别和管理它的全部信息）
> ```
>
> **"文件"这个概念其实是"名字"和"inode"的组合。** 名字是给**人**用的，inode 是给**内核**用的。

## 二、inode 存在磁盘哪里（p17–p21）

课件 p17 用了**连续八页**（p17 到 p24）来铺垫同一个答案，这里一次性讲清。

### 存放位置（p17）

> *"**i-nodes are stored at the front of each region of disk that contains a Unix file system.**"*
> （**i-node 存放在每个包含 Unix 文件系统的磁盘区域的前部**。）

**"region（区域）"** 指磁盘被划出的**分区/文件系统**。所以：

```
一个 Unix 文件系统（一个分区）的磁盘布局：

┌──────────────┬──────────────┬─────────────────────┬──────────────┐
│  Boot Block  │  Super Block │  i-node 表           │  数据块        │
│  （引导块）   │  （超级块）   │  inode1 … inodek     │  Block1 … n   │
└──────────────┴──────────────┴─────────────────────┴──────────────┘
   固定占用        固定占用        ★ inode 全在这里 ★      文件内容在这里
```

**这张布局图来自课件 p25–p26 的目录示例页**，课件把 `Boot Block`、`Super Block`、`i-node 1 … i-node k`、`Data Block 1 … Data Block n` 画在同一张图上。

| 区域 | 作用 |
|---|---|
| **Boot Block 引导块** | 系统启动时用 |
| **Super Block 超级块** | 记整个文件系统的全局信息 |
| **i-node 表** | **这个文件系统里所有 inode 连续存放** |
| **数据块** | 文件的实际内容 |

> [!note] 课件未展开 Boot Block 与 Super Block
> 课件 p25/p26 的图上标出了这两块，但**没有讲解它们的内容**。**本篇不做推测。**
> 上一句"Super Block 记全局信息"是按 Unix 通行定义补的 —— **背景补充**。

## 三、i-number：inode 的编号（p20）

> *"A regular file has a number called the **i-number**, which is an **index into an array of the i-nodes** on disk. **Each i-node corresponds to a unique i-number (index).**"*
> （普通文件有一个叫 **i-number** 的数，它是**磁盘上 inode 数组的下标**。**每个 inode 对应一个唯一的 i-number（下标）。**）

**这就是 i-number 的定义，一个数组下标。**

```
磁盘上的 i-node 表（连续数组）：

  下标/i-number    inode 内容
  ─────────────   ──────────────────────────────
      0           （保留，不用）
      1           inode 1  ─┐
      2           inode 2   │
     ...          ...      │  连续存放
    230           inode 230 │ ★ 这就是"i-number 230"的含义
     ...          ...      │
      k           inode k  ─┘
```

> [!tip] 为什么不直接用地址当编号
> 因为**编号和位置分离**：磁盘上的 i-node 表是**连续数组**，所以"i-number 230"就是**第 230 项**。
> 好处是**紧凑**——一个整数就够定位一个 inode。
>
> 这也解释了为什么 `ls -i` 能直接打出 inode 号：它就是下标。

## 四、目录文件：名字到 i-number 的表（p25、p26）

**这是整篇的答案所在。** 课件 p25/p26 给出的完整示例：

**磁盘布局：**

```
Boot Block | Super Block | i-node 1 … i-node k | Data Block 1 … n
```

**某个目录文件的内容（这是关键）：**

| **i-number** | **File name** |
|---|---|
| **123** | **`.`** |
| **247** | **`..`** |
| **220** | `dirB` |
| **230** | `My1.dat` |

**读这张表：**

- 这个目录里有 **4 个条目**
- 每个条目**只有两列**：**i-number** 和 **File name**
- **没有任何文件内容、没有任何元信息** —— 只有"名字 ↔ 编号"的对应

> [!warning] 这一张表回答了 p16 那个问题
> **文件名存在目录文件里。**
>
> 所以推论立刻成立：**同一个 inode，可以被不同的目录用不同的名字引用；同一个名字，可以在不同目录里对应不同的 inode。**
>
> - **两个同名文件** → 两个不同 inode，各自的目录里各有一条记录 → [[层次结构与路径名|层次结构与路径名]] 里那两个 `My1.dat`
> - **一个文件多个名字** → 同一个 inode 被多个目录各记一条 → [[硬链接与符号链接|硬链接与符号链接]]

### `.` 和 `..` 的来由（p25）

对照 [[当前工作目录]] 里说的"`.` 和 `..` 是真实存在的条目"：

| 条目 | i-number 123 / 247 指向 | 实现的功能 |
|---|---|---|
| **`.`** | **指向这个目录自己** | "当前目录" |
| **`..`** | **指向父目录** | "上一级" |

**于是 `..` 不需要任何特殊逻辑** —— 它就是一条普通的"名字 → i-number"记录，只不过那个 i-number 恰好是父目录的编号。内核沿着它走，就回到了上一级。

> [!tip] 这也解释了当前目录被删的情况
> 因为 cwd 的本质是**"指向某个 inode"**，而不是"存了一个路径字符串"。
> 所以目录被 `rm -rf` 掉之后，你的 cwd 指向的 inode **仍然存在**（只要还有进程引用它），你还能在里面操作文件 —— 只是 `pwd` 打出来的路径**已经不存在了**。
> 参见 [[当前工作目录]] 的那个警告。

## 五、完整链路

把 p15 到 p26 全部串起来，就是"**从名字到内容**"的完整过程：

```
  你要访问 /dirA/My1.dat
              │
      ① 逐级查名字（name resolution）
         从 / 出发，在根目录里找 "dirA"  → 得到一个 i-number
         拿这个 i-number 找到 dirA 的 inode → 知道它的数据块在哪
         把 dirA 的数据块当目录读出来 → 在里面找 "My1.dat"
                                     → 得到 i-number 230        ← p25 那张表的第 4 行
              │
      ② 拿 i-number 查 inode
         到 i-node 表的第 230 项取 inode              ← p20 的"下标"
              │
      ③ 读 inode
         得到：类型、权限、UID、大小、★ 数据块位置 ★
              │
      ④ 读数据块
         按 inode 指的位置读出内容                      ← p25 的 Data Block
              │
           文件内容
```

| 步骤 | 涉及的概念 | 笔记 |
|---|---|---|
| ① 逐级查名字 | **name resolution** | [[名称解析与文件大小上限]] |
| ② 查 inode | **i-number 是下标** | 本文第三节 |
| ③ 读 inode | **inode 里有什么** | 本文第一节 |
| ④ 读数据块 | **多级间接指针** | [[名称解析与文件大小上限]] |

> [!warning] 第 ① 步是课件花 8 页铺垫的那一步
> 回头看课件 p17–p24 这 8 页，标题都是同一句：**"Where is i-node stored? And how can we find the i-node of a file?"**
>
> 这个"铺垫—揭晓"的教学手法（先问问题、逐页加信息、最后给答案）在本课程里出现过好几次：[[进程是什么]] 的 $s(e,i)$、[[硬链接与符号链接|硬链接与符号链接]] 的对比都是同一套路。
> **课件不是在罗列事实，是在演示"怎么推导"。**

## 一句话

> 文件名**不存在 inode 里**，而是存在**目录文件**中 —— 目录文件就是一张 **"File name ↔ i-number"** 的表；**i-number 是 inode 数组的下标**，inode 集中存在文件系统分区的前部，里面记着类型、权限、大小和**数据块位置**，唯独没有文件名。
