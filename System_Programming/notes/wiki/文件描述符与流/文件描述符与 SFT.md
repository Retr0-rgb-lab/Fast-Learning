# 文件描述符与 SFT

> **一句话**：**文件描述符（fd）就是一个整数，它是"进程 fd 表"的下标**。fd 表的每一项指向"系统文件表（SFT）"的一个条目，SFT 里记着"这个文件是读还是写、有没有锁、读写偏移到哪了"。**所以两个进程可以共享同一个文件，却各有自己的读写位置。**

课件对应 L03 p35–p37。课件原文见 [03-Unix-File-System](<../../raw/03-Unix-File-System.pdf>)。

## 完整场景：两层表是为了什么

**先把要解决的问题摆出来。** 两个进程都要读写**同一个文件**，而且**各自维护自己的读写位置**：

```
进程 A 读文件：从头读，读到第 100 字节
进程 B 也读同一个文件：也要从头读，读到第 50 字节
                       ↑
              ★ 两者的位置必须互不干扰 ★
```

如果"读写偏移"直接记在文件上，两个进程就会互相踩。**Unix 的解法是把信息拆到两张表里。**

## 一、两张表（p36）

### 进程 fd 表 → 系统文件表 SFT

课件 p36 给出 SFT 条目里存什么：

> *"SFT entry contains information about: **whether a file is opened for read/write**, **permission**, **lock**, **read/write offset** etc."*
> （SFT 条目包含这些信息：**文件是为读还是为写打开的**、**权限**、**锁**、**读写偏移**等。）

**并且课件点出了一条关键性质**：

> *"**Several entries in SFT may point to the same physical file.**"*
> （**SFT 里可以有多个条目指向同一个物理文件。**）

### 结构图

```
┌─────────────────────────────────────┐
│  进程 A 的 fd 表（用户态）            │
│  ┌─────┬─────┬─────┬─────┐          │
│  │  0  │  1  │  2  │  3  │           │
│  └──┬──┴──┬──┴──┬──┴──┬──┘          │
└─────┼─────┼─────┼─────┼─────────────┘
      │     │     │     │
      ▼     ▼     │     ▼
┌─────────────────────────────────────┐
│  系统文件表 SFT（内核态，全系统一份）   │
│  ┌─────────────────┐                │
│  │ SFT #10         │◀──┐            │
│  │  打开方式：只读  │   │            │
│  │  权限：…        │   ├── A 的 fd3 │
│  │  锁：无         │   │            │
│  │  ★ 偏移：100 ★ │   │            │
│  └────────┬────────┘   │            │
│           │            │            │
│  ┌────────▼────────┐   │            │
│  │ SFT #11         │◀──┴────────────┤
│  │  打开方式：读写  │                │
│  │  锁：无         │                │
│  │  ★ 偏移：50 ★  │                │
│  └────────┬────────┘                │
│           │                         │
└───────────┼─────────────────────────┘
            ▼
      inode 230（同一个文件）
```

**读这张图的关键两点：**

| 事实 | 后果 |
|---|---|
| **"读写偏移"在 SFT 里** | 所以两个进程**各有各的偏移**，互不干扰 |
| **"多个 SFT 条目可指向同一物理文件"** | 所以 A 和 B 打开的是**同一份数据**，但状态独立 |

> [!tip] 为什么偏移不能放在 inode 里
> inode 是**文件本身的属性**（类型、权限、大小），**全局只有一份**。
> 而"读到哪了"是**某次打开的状态**，一次打开一个值。
>
> **属性 vs 状态 —— 这就是拆成两张表的根本原因**，和 "[[../inode 与链接/inode 与目录文件|inode 与目录文件]]"里"名字不在 inode 里"是同一种设计思路。

## 二、fd 本身就是一个下标（p37）

> *"When new files are opened, it is assigned the **lowest available FD**."*
> （打开新文件时，会分配**最低的可用 fd**。）

**这就是 fd 的全部含义** —— 进程 fd 表里的**下标**。

**所以 fd 是"进程内局部"的**：同一个文件在进程 A 里可能是 3，在进程 B 里可能是 7。**fd 本身不指向文件，只指向"我这本表的第几行"。**

### 三个自动打开的文件（p37）

> *"**Three files are opened automatically**: `STDIN_FILENO`; `STDOUT_FILENO`; `STDERR_FILENO`"*

课件把这三个名字和它们的编号直接对应：

| 宏 | 名字 | 编号 | 指向 |
|---|---|---|---|
| **`STDIN_FILENO`** | 标准输入 standard input | **0** | 你敲键盘的地方 |
| **`STDOUT_FILENO`** | 标准输出 standard output | **1** | 正常输出的地方 |
| **`STDERR_FILENO`** | 标准错误 standard error | **2** | 报错的地方 |

**"三个常量 0、1、2 in `unistd.h`"** —— 课件明确了这三个常量定义在 `unistd.h` 头文件里。

> [!warning] 为什么一上来就是 0、1、2
> 因为进程一启动，Shell 就已经替你把这三个"连到终端"的 fd 开好了。
> 你的程序**一进 `main()` 就已经能 `read(0, ...)` 和 `write(1, ...)`**，不用自己 `open` 任何东西。
>
> **这正是 Unix 一切皆文件的直接后果** —— 终端也是文件（见 [[../文件系统结构/文件类型|文件类型]]），所以"键盘"和"屏幕"能被当成普通的 fd 0 / 1 来用。

### 三个 fd 的实际用途

| fd | 通常连到 | 用途 |
|---|---|---|
| **0** | 键盘 | 读用户输入 |
| **1** | 终端 | 正常输出 |
| **2** | 终端 | **错误信息** |

**为什么 `1` 和 `2` 要分开？** 课件没有解释。按 Unix 的通行实践：

```
$ ls /nonexistent > out.txt
```

这样**报错还是显示在屏幕上**（因为只重定向了 fd 1），而正常输出进了文件。**分开才能让你只丢弃或重定向正常输出、把错误保留。**

> ⚠️ **这个理由课件 L03 没有给出。** 课件 p37 只是并列列出三个文件和它们的编号，**没有讲为什么要分成 1 和 2**。上面这段是根据 Unix 通行实践补的，**背景补充**。

## 三、fd 是"与设备无关"的接口（p35）

课件 p35 做了这一讲最重要的区分：

> *"Within C programs, a file is accessed either by **file descriptors** or by **file pointers**, which provide **logical names (handles)** for performing **device-independent I/O**."*
> （在 C 程序里，文件要么通过**文件描述符**访问，要么通过**文件指针**访问；它们提供**逻辑名字（句柄）**，用来进行**与设备无关的 I/O**。）

> *"The Unix file system calls use file descriptors（via `open`, `read`, `write`, `close`, `fsync`, `lseek`, and `ioctl`）. The ANSI C I/O library uses..."*
> （Unix 文件系统调用使用**文件描述符**（通过 `open`、`read`、`write`、`close`、`fsync`、`lseek` 和 `ioctl`）。ANSI C 的 I/O 库使用……）

**"device-independent I/O"（与设备无关的 I/O）** 这句话回扣了 [[../文件系统结构/文件类型|文件类型]] 那一篇的核心思想 —— 同一套 `open`/`read`/`write`，既能操作磁盘文件，也能操作键盘、屏幕。

### 两套访问方式的分工（p35）

| | **文件描述符 fd** | **文件指针 FILE\*** |
|---|---|---|
| 属于谁 | **内核**接口 | **C 标准库**接口 |
| 头文件 | `<unistd.h>` `<fcntl.h>` | `<stdio.h>` |
| 函数 | `open` `read` `write` `close` `lseek` `fsync` `ioctl` | `fopen` `fprintf` `scanf` `fclose` |
| 特点 | **底层、直接、无缓冲** | **上层、带缓冲、格式化** |
| 笔记 | **本篇** | [[../文件描述符与流/FILE 流与格式化输入输出\|FILE 流与格式化输入输出]] |

> [!tip] 关系：FILE\* 是 fd 的"包装"
> [[../文件描述符与流/FILE 流与格式化输入输出|下一节]] 会讲：`FILE` 结构里**同时存着一个缓冲区和一个 fd** —— 所以 **FILE 指针是"句柄的句柄"**（课件 p42 的原话）。
>
> **两个层次都能用，且可以混用。**

## 四、fd 表的三层含义

| 层次 | 是谁 | 记什么 | 笔记 |
|---|---|---|---|
| **fd 那个整数** | 进程 | "我这张表的第几行" | 本篇第二节 |
| **fd 表项** | 进程 | 指向哪个 SFT 条目 | 本篇第一节 |
| **SFT 条目** | 内核，全系统一份 | 打开方式、权限、锁、**读写偏移** | 本篇第一节 |
| **inode** | 内核 | 类型、权限、大小、数据块位置 | [[../inode 与链接/inode 与目录文件\|inode 与目录文件]] |

**从 fd 到内容，一条完整的路：**

```
fd = 3
  │ 进程 fd 表第 3 项
  ▼
SFT #10（打开方式=只读，偏移=100）
  │ 记着指向哪个物理文件
  ▼
inode 230（数据块位置）
  │ 按指针跳
  ▼
数据块 → 文件内容
```

> [!warning] 最后一层值得强调
> **从 fd 到 inode 是"指针"，从 inode 到数据块是"指针"，从名字到 inode 是"查表"** —— 两类操作完全不同。
>
> - **查表**：name resolution，见 [[../inode 与链接/名称解析与文件大小上限|名称解析]]
> - **指针跳转**：本篇 + [[../inode 与链接/名称解析与文件大小上限|多级间接寻址]]
>
> **"名字 → fd"这一段（查表）之后就全是"跟着指针走"了。**

## 一句话

> **fd 是进程 fd 表的下标**（打开新文件时分配**最低可用**号，**0/1/2 预留给 stdin/stdout/stderr**）；fd 表指向**系统文件表 SFT**，SFT 里记着**打开方式、权限、锁、读写偏移**，且**多个 SFT 条目可以指向同一个物理文件** —— 这就是两个进程能共享文件却各有各的读写位置的原因。
