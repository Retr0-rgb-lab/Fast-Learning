# I/O 重定向与 dup

> **一句话**：**重定向就是改"进程的 fd 表某一项指向哪个 SFT 条目"。** `>` 让 fd 1 不再指向终端、改指到文件；`dup` 提供了一种**在程序里做同样的事**的办法 —— 复制一个已有 fd 到**最低可用号**。

课件对应 L03 p54–p61。课件原文见 [03-Unix-File-System](<../../raw/03-Unix-File-System.pdf>)。

## 完整场景：重定向到底是什么

**先把要改的东西说清楚。** [[../文件描述符与流/文件描述符与 SFT|文件描述符与 SFT]] 建立了这两层表：

```
进程的 fd 表 → 系统文件表 SFT → inode
```

**重定向改的只是第一层**：让某个 fd 指向**另一个** SFT 条目。

**重定向前后对照（以 `ls > myfiles` 为例）：**

```
【重定向前】
  进程 fd 表              SFT
   ┌────┐
   │ 1  │ ────────────▶ SFT #7 { 打开方式=写, 偏移=0, 指向=终端 }
   └────┘
      ↑
   STDOUT_FILENO → 终端


【执行 ls > myfiles 之后】
  进程 fd 表              SFT
   ┌────┐
   │ 1  │ ────────────▶ SFT #42 { 打开方式=写, 偏移=0, 指向=myfiles }
   └────┘                ────────────▶ inode of myfiles
      ↑
   ★ 只有这一行变了 ★

  SFT #7（终端那条）还在，只是没有 fd 指向它了
```

> [!warning] 一个关键结论：重定向**不影响程序本身**
> `ls` 这个程序**完全不知道**自己被重定向了。它调的仍然是 `write(1, buf, n)` —— **fd 还是 1，还是"标准输出"**。
>
> 变的只是**"fd 1 在 SFT 里对应哪个条目"**。
>
> 这就是为什么[[../Unix 总览/Unix 哲学与工具组合|组合能力在程序之外]] —— `ls` 从来没被改过一行代码。

### 三种重定向符号

| 符号 | 改哪个 fd | 方向 | 文件打开方式 |
|---|---|---|---|
| **`>`** | **fd 1**（stdout） | 输出 → 文件 | **清空**（`O_TRUNC`） |
| **`>>`** | **fd 1** | 输出 → 文件 | **追加**（`O_APPEND`） |
| **`<`** | **fd 0**（stdin） | 文件 → 输入 | 只读 |

> [!tip] `>` 的"清空"性质来自打开方式
> `>` 用的是 `O_TRUNC`（truncate），`>>` 用的是 `O_APPEND`。
> 这解释了 [[../文件描述符与流/FILE 流与格式化输入输出|文件类型]] 那一篇提到的 `w`（清空）与 `a`（追加）之分 —— **Shell 的 `>` 就是 `w`，`>>` 就是 `a`。**

**fd 2（stderr）默认不被重定向**，这就是[[../文件描述符与流/文件描述符与 SFT|`1` 和 `2` 分开]]的实际用途：

```bash
$ ls /nonexistent > out.txt
```

**报错还显示在屏幕上**，只有正常输出进了 `out.txt`。

## 二、dup：程序里怎么实现重定向（p56）

### 课件的定义

> *"**`int dup(int oldfd)`** duplicates the given file descriptor to the **lowest numbered unused file descriptor** in the file descriptor table."*
> （**`dup`** 把给定的文件描述符**复制到 fd 表中编号最低的未使用 fd**。）

**三个要点：**

| 要点 | 含义 |
|---|---|
| **复制 fd** | 不是移动，是**复制** —— 原 fd 仍然有效 |
| **复制到最低可用号** | 这正是"重定向能指定 0/1/2"的原因 |
| **复制的是"指向 SFT 的指针"** | 两个 fd **共享同一个 SFT 条目** ⇒ **共享读写偏移！** |

### `dup` 的完整实现逻辑（课件 p56–p61 的代码）

课件用**同一个例子反复讲了六页**（p56 到 p61），因为它是一个完整的"从 C 程序里模拟 `>`"的过程。先把它拆开：

**目标**：让 `/bin/ls -l` 的输出进到文件里去，而不是终端。

```c
#include<stdio.h>
#include<fcntl.h>
#include<unistd.h>

char* cmd[] = {"/bin/ls", "-l", 0};

int main(int argc, char* argv[]){
        int fd = open(argv[1], O_WRONLY | O_CREAT | O_TRUNC, 0644);
        /* … */
}
```

**按"要做什么"的顺序拆成三步：**

| 步 | 做什么 | 用什么 | 为什么 |
|---|---|---|---|
| **① 备份** | 把原来的 **fd 1（stdout）**复制到一个**临时 fd** | `dup(1)` | **必须先备份**！等会儿 fd 1 要被改掉 |
| **② 让 fd 1 空出来** | **关掉 fd 1** | `close(1)` | `dup` 只会填**未使用**的号；**fd 1 还在用，它不会去填 1** |
| **③ 重定向** | 把 `open` 得到的 `fd` **复制到 fd 1** | `dup2` 或 `dup`+`close` | 这样"标准输出"就指向了文件 |

**完整的经典写法：**

```c
int fd = open(argv[1], O_WRONLY | O_CREAT | O_TRUNC, 0644);
/* fd 通常是 3（0/1/2 被占用）*/

int saved = dup(1);        /* ① 备份 stdout → saved（通常是 4 或 3）*/

close(1);                   /* ② 腾出 fd 1 */

dup(fd);                    /* ③ ★ fd 被复制到最低可用号 = 1 ★ */
                            /*    现在 fd 1 == fd 指向同一个 SFT */

close(fd);                  /* ③b 原 fd 不用了 */
close(saved);                /* ③c 备份也不用留了 */
```

> [!warning] 第 ② 步 `close(1)` 是最容易漏掉的一步
> **如果忘了 `close(1)`**，`dup` 会把 `fd` 复制到**下一个可用号（比如 4）**，**而不是 1**。
> **结果：`/bin/ls` 的输出还是打到终端去了**，重定向静默失效。
>
> 这是 `dup` 用起来最别扭的地方 —— **它不给"指定目标号"的接口**。

### `dup2`：直接指定目标号（p56 之后课件代码里的做法）

正因上面那个坑，POSIX 提供了 **`dup2(oldfd, newfd)`**：

```c
int newfd = dup2(fd, 1);   /* ★ 直接把 fd 复制成 fd 1 ★ */
```

**它把"关掉再 dup"这两步合成了一个原子操作**，所以不需要 `close(1)`。

| | `dup(oldfd)` | `dup2(oldfd, newfd)` |
|---|---|---|
| 目标号 | **只能是最-lowest 可用号** | **由你指定** |
| 要先 `close` 吗 | ✅ **要**，否则填不进想要的位置 | ❌ **不用**，会自动关掉 `newfd` |
| 能定位到 1/2 吗 | 只能"碰巧" | ✅ **直接指定** |

> [!note] 课件讲的是 `dup`，`dup2` 是补充
> 课件 p56 的定义句只提到 **`dup`**。六页的代码是在演示"用 `dup` 实现重定向"这个思路。
> **`dup2` 是 POSIX 后来加的便捷版本** —— 上面关于 `dup2` 的对照是按 Unix 通行实践补的，**背景补充**，不是课件内容。

### 三个变体的语义差异（系统调用层 vs Shell 层）

| | 做什么 |
|---|---|
| `dup(1)` | 把 **fd 1** 复制到最低可用号（不关 1） |
| `dup2(fd, 1)` | 把 **fd** 复制成 **fd 1**（自动关掉原来的 1） |
| Shell 的 `>` | Shell 做上面那套三步，让被启动程序的 **fd 1** 指向文件 |

**Shell 的 `>` 是"给被启动的程序准备好的 fd 表"** —— 所以程序本身不需要知道任何事。

## 三、dup 的一个副作用：共享偏移

> [!warning] 两个 fd 指向同一个 SFT ⇒ 共享读写位置
> ```
> fd 3 ──┐
>        ├──▶ SFT #10 { 偏移 = 100 }
> fd 7 ──┘
> ```
> **`dup` 之后，通过 fd 3 读会推进偏移，fd 7 看到的偏移也变了。**
>
> 这和[[../文件描述符与流/文件描述符与 SFT|两个进程各自 `open` 同一文件]]的情况**完全不同** —— 那是两个不同的 SFT 条目，偏移独立。
>
> **差别**：**dup 是"同一个打开"，再 open 是"两次打开"。**
>
> ⚠️ **课件 p36 讲了"SFT 里可以有多个条目指向同一个物理文件"，但没有把"一个条目被多个 fd 引用"这个情况单独讲。** 上面这段是按 SFT 的结构推出的，**背景补充**。

## 四、这套机制解决的问题清单

把重定向、`dup`、fd 表、SFT 串起来，它们共同支撑了这些：

| 能力 | 靠什么实现 |
|---|---|
| `ls > file` | 改 **fd 1** 的指向 |
| `ls >> file` | 同上，但用 `O_APPEND` |
| `cmd < input` | 改 **fd 0** 的指向 |
| `cmd > /dev/null` | 改 fd 1 指向**字符设备** `/dev/null` |
| `cmd 2>&1` | 把 fd 2 复制到 fd 1（`dup2(2,1)`）→ **错误也进同一个地方** |
| `dup(oldfd)` | 程序里复制 fd，**共享同一个 SFT** |
| 管道 `a \| b` | a 的 fd 1 和 b 的 fd 0 指向**同一个管道 SFT** |

> [!tip] `2>&1` 的读法
> **`2>&1` 是"把 fd 2 复制到 fd 1"**（Shell 语法里 `2>&1` 的 `&` 表示"复制 fd 1 的指向"）。
> 放在 `>` 前后**意思完全不同**：
> | 写法 | 顺序 | 结果 |
> |---|---|---|
> | `cmd > f 2>&1` | 先把 1 指到 f，再让 2 指到 1 | **正常输出和错误都进 f** |
> | `cmd 2>&1 > f` | 先让 2 指到 1（此时 1 是终端），再把 1 指到 f | **错误进终端、正常输出进 f** |
>
> ⚠️ **课件 L03 只讲了重定向的基本概念（p54–p55），没有讲 `2>&1` 这类组合重定向。** 上表是根据 Shell 通行语义补的，**背景补充**。

## 一句话

> **重定向 = 改进程的 fd 表项指向另一个 SFT 条目**（`>` 改 fd 1 且 `O_TRUNC` 清空、`>>` 改 fd 1 但 `O_APPEND` 追加、`<` 改 fd 0），**被执行的程序完全不知情**；程序里可以用 **`dup`（复制到最低可用号，需先 `close` 腾位）或 `dup2`（直接指定目标号）** 实现同样的事，代价是两个 fd **共享同一个 SFT 条目因而共享读写偏移**。
