# 管道与进程间通信

> **一句话**：**`pipe()` 一次给你两个 fd —— `fd[0]` 读、`fd[1]` 写。** 父进程把**写端**留给子进程、子进程把**读端**留给父进程，数据就能从子进程流到父进程。它是内核提供的**最基础的进程间通信机制**。

课件对应 L03 p62–p63。课件原文见 [03-Unix-File-System](<../../raw/03-Unix-File-System.pdf>)。

## 完整场景：为什么需要它

[[../进程与线程/进程是什么|进程]]之间**默认是隔离的** —— 一个进程不能直接读另一个进程的内存。理由见 [[../进程与线程/进程是什么|进程是什么]]："资源按进程分配"。

于是要传数据就得有专门的机制。**管道是其中最简单的一个**，而它的巧妙之处是：

> **它不给你一个"发送函数"，它给你的是两个 fd。**
>
> 所以**父进程和子进程对管道的所有操作，用的就是普通的 `read`/`write`** —— 不需要任何新的 API。

## 一、pipe 的原型（p62）

课件 p62 给出的原型：

```c
int pipe(int fd[2]);
```

### 三个要点

| 要点 | 课件原文 | 含义 |
|---|---|---|
| **返回两个 fd** | *"System call `pipe()` **returns two file descriptors** by which we can access the input/output of a pipe"* | 一个调用，**两个** fd |
| **方向固定** | *"Pipe **`fd[1]` is for writing**; **`fd[0]` is for reading**"* | **`fd[1]` 写、`fd[0]` 读**，下标和方向相反 |
| **返回值** | *"Return: **0 success; -1 error**"* | 遵循 `int` 的失败约定 |

> [!warning] 下标和方向是**相反**的，这是最容易记错的地方
> ```
> fd[0]  →  读  ← 读起来像"第 0 个输入"
> fd[1]  →  写
> ```
> **记住"0 是输入、1 是输出"这个对应**，别去记 `pipe` 本身。
> 同样的对应在别处也成立：**fd 0 = stdin（输入）、fd 1 = stdout（输出）** —— 见 [[../文件描述符与流/文件描述符与 SFT|0/1/2]]。

**"管道是一个 I/O 机制"**（课件原话：*"an I/O mechanism"*）—— **所以它有 SFT 条目、有读写偏移、可以用 `read`/`write`。**

## 二、完整的父子通信例子（p63）

课件 p63 给了代码，先把结构讲清楚，再逐行看。

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <string.h>

int main(){
    int fd[2];
    pipe(fd);              /* fd[0] is for read and fd[1] is for write */

    pid_t child = fork();
    if (child == 0){      /* child process */
        close(fd[1]);     /* ★ 子进程关掉写端 —— 它只读 ★ */
        /* … 从 fd[0] 读 … */
    } else {              /* parent process */
        close(fd[0]);     /* ★ 父进程关掉读端 —— 它只写 ★ */
        /* … 往 fd[1] 写 … */
    }
}
```

### 三个必须理解的点

**① `fork` 之后两个进程各有一份 `fd[]`**

[[../进程管理/fork 创建进程|`fork` 复制整个进程]]，所以 `fd[0]` 和 `fd[1]` 这两个数字**在父子两边都有**。

**关键区别不在数字，而在它们各自指向哪个 SFT 条目：**

```
pipe() 之后（fork 之前）：

  fd[0] ──▶ SFT #A（管道的读端）
  fd[1] ──▶ SFT #B（管道的写端）
              ↑ 这是内核里的同一个管道对象

fork 之后：

  父进程：fd[0] ──▶ SFT #A     fd[1] ──▶ SFT #B
  子进程：fd[0] ──▶ SFT #A     fd[1] ──▶ SFT #B
                                   ★ 同一个管道对象 ★
```

**所以：父进程往 `fd[1]` 写的数据，子进程从 `fd[0]` 就能读到。** 因为它们操作的是同一个内核管道。

**② 各自 `close` 掉用不上的那一端**

这是本篇**最关键、也最容易被跳过的实践点**：

| 进程 | `close` | 为什么 |
|---|---|---|
| **子进程** | `close(fd[1])` | **它只读**。留着写端没用 |
| **父进程** | `close(fd[0])` | **它只写**。留着读端没用 |

> [!warning] 不关会怎样：父进程永远等不到 EOF
> **管道的"写完了"的信号 = 所有写端都被关闭。**
>
> 设想不 `close`：
> ```
> 父进程：写完数据 → 退出前 close(fd[1])
> 子进程：读完数据 → 循环 read 到返回 0 → 认为"写完了" → 退出
> ```
> 看起来正常。但如果**父进程不关自己的 `fd[0]`**：
> ```
> 子进程：读数据 → 读完了 → 再 read → ★ 阻塞等待 ★
>         （因为它自己那份 fd[1] 还没关，父进程那份 fd[1] 也还在）
> ```
> **子进程会永远卡在 `read` 上** —— 因为只要还有任何一个写端开着，它就一直"可能还有数据"，`read` 就一直阻塞。
>
> **这就是 `close` 的真正理由：不是省资源，是"发信号"。**
>
> ⚠️ **课件 p63 的代码确实写了这两个 `close`，但没有解释为什么。** 上面的机制说明是根据 Unix 通行实践补的，**背景补充**。

**③ 方向固定，所以要各自关掉反向的**

因为 `fd[0]` 只能读、`fd[1]` 只能写，子进程要读就得关 `fd[1]`、父进程要写就得关 `fd[0]`。**`close` 在这里的作用是"确保只有该方向的使用者"。**

## 三、管道 vs 文件

> [!tip] 两者的对照（管道是"内存里的文件"）
> | | **普通文件** | **管道** |
> |---|---|---|
> | 内容存在哪 | **磁盘** | **内核内存** |
> | 数据会持久吗 | ✅ 会（关掉还在） | ❌ **不会**（两端都关就没了） |
> | 能重读吗 | ✅ 能（`lseek` 回去） | ❌ **不能**，只能顺序读一遍 |
> | 谁能看到 | 所有进程 | **只有握着对应 fd 的进程** |
> | 有路径名吗 | ✅ 有 | ❌ **没有** |
> | 生命周期 | 直到被删 | **直到所有 fd 关闭** |
> | fd 怎么来 | `open` | **`pipe()`** |
>
> **最后一行是理解管道的钥匙**：管道**没有文件名**，因为它从来不在目录里。它只在内核里存在，靠 fd 被访问。

## 四、Shell 的 `|` 就是这套机制（p63 与 L01 的对照）

[[../Unix 总览/Unix 哲学与工具组合|Unix 哲学与工具组合]] 讲的 `who | sort | lp`，在系统层面是这样实现的：

```
谁创建管道？      ★ Shell ★（不是 who，不是 sort）
      │
      ├─ fork() 出 sort 进程
      │     └─ 把 sort 的 fd 0 接到管道的读端
      │
      ├─ fork() 出 lp 进程
      │     └─ 把 lp 的 fd 0 也接到管道的读端
      │
      └─ who 是前台进程（不 fork），把它的 fd 1 接到管道的写端
```

**于是三个进程共享同一个管道：**

```
   who 的 fd 1 ──┐
                 ├──▶ 管道（内核对象）
   sort 的 fd 0 ─┤
                 │
   lp   的 fd 0 ─┘
```

**这是本篇最重要的实际意义**：

> [!warning] `|` 的能力只在 Shell 层，不在程序里
> **`who`、`sort`、`lp` 三个程序里没有任何一个提到管道。**
>
> 它们只会 `write(1, …)` 和 `read(0, …)`。**管道是 Shell 在外面接上去的。**
>
> 这和 [[../重定向与管道/I O 重定向与 dup|重定向]] 是同一个道理 —— **组合能力在程序之外**。
>
> 区别：
> - **重定向**把 fd 接到**一个文件**上（数据落在磁盘，可重复读）
> - **管道**把 fd 接到**一个内核管道**上（数据在内存里，只流一遍）

## 五、管道与内核职责

[[../Unix 总览/Unix 组成结构|Unix 组成结构]] 列的内核六大职责里有一条：

> *"**inter-process communication**"* —— 进程间通信

**管道就是这条职责最基础的实现之一**（其他还有 socket、信号、共享内存）。

**Unix 通过"给一个新内核对象配两个 fd"来扩展系统**，而不新增系统调用：

| 内核对象 | 用什么系统调用拿到 fd |
|---|---|
| 文件 | `open` |
| **管道** | **`pipe`** |
| socket | `socket`（课件 L01 p21 提到 socket 抽象，**未展开**） |

**这就是"一切皆文件"的完整含义** —— 不只是"接口一样"，**连"怎么拿到手柄"的套路都一样。**

## 六、实践要点

| 事项 | 做法 | 漏了的后果 |
|---|---|---|
| **各关不用的一端** | 子进程 `close(fd[1])`、父进程 `close(fd[0])` | **对方永远等不到 EOF，程序挂死** |
| **方向** | `fd[0]` 读、`fd[1]` 写 | 逻辑反了 |
| **`fork` 前建管道** | 先 `pipe()` 再 `fork()` | 反了就成两个独立管道，父子不通 |
| **管道无持久性** | 数据只流一遍 | 想回读就读不到了 |
| **大数据** | 管道容量有限（Linux 通常 64 KB） | 写多了会**阻塞**，必须交替读写 |

> [!warning] "写多了会阻塞"这个坑
> **管道缓冲区是有限的。** 你往 `fd[1]` 写的数据如果超过缓冲区容量，**`write` 会阻塞**，直到对方开始读。
>
> 所以典型的父子通信循环必须是"**写一点、读一点**"，而不是"先把全部数据写完再读"。
>
> ⚠️ **课件 p62/p63 没有提缓冲区容量和阻塞行为。** 上面这段是根据 Unix 通行实践补的，**背景补充**。

## 一句话

> **`pipe(fd[2])` 一次返回两个 fd（成功 0、失败 -1），`fd[0]` 读、`fd[1]` 写**；因为 [[../进程管理/fork 创建进程|`fork`]] 复制整个进程，父子两边**持有的是同一个内核管道**——所以通信用的就是普通的 `read`/`write`。**父子必须各自 `close` 掉不用的那一端**，否则对方永远等不到 EOF 而挂死。
