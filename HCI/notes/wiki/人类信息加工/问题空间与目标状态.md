# 问题空间与目标状态

> **一句话**：**问题**是"怎么得到我想要的"，**目标状态**是想要的终态，**子目标**是沿途的中期目标；**问题空间**把这三层目标状态加上每一步需要的信息打包成一个可搜索的空间，**解一次题就是让"当前问题状态"这个特征集合挪到与"期望目标状态"重叠**。

课件 Human Part 1『What is problem solving?』一页起（页码未在课件文本层给出，紧接大脑结构那一段之后）。原始 PDF 见 [Human Part 1](<../../raw/02 COMP3423 Human Part 1 2026 09 13.pdf>)。这一页给术语，主线 A 的后续几页给策略。

## 五个术语

| 术语 | 英文 | 课件定义 |
|---|---|---|
| 问题解决 | problem solving | strategies, means, and procedures to achieve a goal（达成一个目标所用的策略、手段与程序） |
| 问题 | problem | **How to get what I want?** |
| 目标状态 | goal state | the desired **end state** or solution of the problem solving activity |
| 子目标 | sub goal | middle-term goal **along the way** to solving a problem |
| 问题空间 | problem space | short-, middle-, and long-term **goal states** and the **information needed at each step** |

注意两个定义的写法差别：问题被定义成一个**问句**，目标状态被定义成一个**名词**。问句会被解答，名词只会被抵达。

## 问题空间里装着什么

课件『Decisions / Short-term working memory』一页把"问题空间"拆成两栏，对应两种记忆：

| 短时工作记忆 Short-term working memory | 长时记忆 Long-term memory |
|---|---|
| 决策 Decisions（yes / no） | 实务知识 Practical knowledge |
| 当前问题状态 current problem state | |
| （若干个）目标状态 (several) goal state(s) | |
| 子目标 sub goals | |
| 生效中的程序 active procedures | |

**为什么必须是短时工作记忆？** 因为解题过程中要反复读写"我现在在哪、我还剩什么子目标、我正在用哪套程序"。这几样东西每走一步都变，长时记忆存不住也不该存。**长时记忆只负责提供"程序本身"（practical knowledge）** —— 这就是为什么"专家"和"新手"的差别是长时记忆里有更多可用程序，而短时工作记忆的结构两者是一样的。

> [!warning] 常见错误
> 问题空间**不是**一张地图，不是一棵树，也不是一个搜索算法。它是"目标状态的序列 + 每一步所需信息"的集合。这个定义直接决定了后面所有策略的性质：策略只是**在这个集合里挑下一步往哪走**。

## 解题就是让 X 挪到与 Y 重叠

课件『Current problem state / Desired goal state』一页的图是这一页的核心，也是整个问题解决理论的原子模型：

- **X = 当前问题状态 current problem state**，标注为"Distinctive set（特征集合）"
- **Y = 期望目标状态 desired goal state**，也标注为"Distinctive set（特征集合）"
- 两个集合的交点标为 **Intersection**
- 课件原话：*"Solving a problem: X should change so to overlap Y"*

写成集合式就是：

$$
X \cap Y = \varnothing \quad\xrightarrow{\ \text{解题：施加一串操作}\ }\quad X' \cap Y \neq \varnothing
$$

课件还在 X 与 Y 之间标了两个词：**improving** 与 **deteriorating**。任一步操作只有两种结果：更接近 Y（improving），或者更远离 Y（deteriorating）。**"更接近"不等于"每步都 improving"** —— 能不能容忍 deteriorating 的步骤，正是区分不同策略的那把尺子。

## 目标满足常常是不完全的：good-enough solution

课件紧接着这张图就写了 **Goal states: Often, goal satisfaction is incomplete: a good-enough solution**。

**为什么必然不完全？** 因为 Y 是一个"特征集合"，而现实中把 X 挪到与 Y 完全重合往往代价无穷大，或者根本不存在这样的操作序列。人**不会**继续搜下去，而是在"已经足够接近"的地方停手。停下的那个点就是 good-enough solution（够好了的解）。

> [!important] 这一条有直接的设计含义
> 判据"够好了"是**用户自己定的**，不是系统定的。系统若只提供"完全满足"的出口，用户就会一直点下去（见 [[随机试错与新手困境]] 里"疯狂点击从这里开始"那段）。**提供一个可接受的停手点，比提供最优解更能减少点击。**

## 目标分解 goal decomposition

课件『Goal decomposition / mission / business goals』一页给出定义：**breaking down a complex problem into smaller ones by determining sub goals**。给了一条三层链：

```
Goal state:   mission            使命
   ↓
Sub goal:     business goals     业务目标
   ↓
Sub sub goal: targets            具体指标（e.g. 5% up in two years）
```

**"子子目标"（sub sub goal）这一档不是凑数**：课件特意给了一个数字例子 —— "5% up in two years"（两年内增长 5%）。**一个模糊的"多赚钱"不能指导任何操作，"两年内 5%"可以。** 子目标的作用就是把抽象的使命压到**可判定是否达成**的程度。

"Business Process Change"这个标题在课件里紧挨着这条链出现（p30）—— 课件把目标分解直接接到了业务流程改造上。

## 问题连续统 The problem continuum

课件『The problem continuum』一页用一张把 **确定的一端**和**不确定的另一端**对置的图。左边一列（自下往上）：

| 端点 | 课件的三个标签 |
|---|---|
| **理性问题解决 Rational problem solving** | 生存导向 Survival focus |
| ↳ 情境 | 确定性情境 Deterministic situations |
| ↳ 问题 | 良定义问题 Well-defined problems |
| ↳ 决策 | 结构化决策 Structured decisions |
| ↳ 策略倾向 | 类比 Analogy |

右边一列（自上往下）：

| 端点 | 课件的三个标签 |
|---|---|
| **创造性问题解决 Creative problem solving** | 机会寻求 Opportunity seeking |
| ↳ 情境 | 概率性情境 Probabilistic situations |
| ↳ 问题 | 病态定义问题 Ill-defined problems |
| ↳ 决策 | 非结构化决策 Unstructured decisions |
| ↳ 策略倾向 | 智能 Intelligence — 收敛 convergence、学到的适应 learned adaptation、对情境的理解 understanding of contexts |

课件在两端之间还点了四个词，构成中间地带：**类比（Analogy）**、**连续性（Continuity）**、**断裂（Disruption）**、**意外收获（Serendipity）**。

- **连续性 Continuity**：沿着原有方向继续推。
- **断裂 Disruption**：把方向整个换掉。
- **意外收获 Serendipity**：不是自己找的，是撞上的。

注意这四个词在课件图上是**横跨中段的**，不是在两端各归一个。**类比既是连续也是断裂** —— 详见 [[类比推理]]。

> [!warning] 常见错误
> 连续谱不是"两个极端二选一"。同一个任务可以同时有良定义的部分和病态定义的部分，**人在两端之间移动**。设计时真正的工作是判断"**这一次**具体动作落在谱上哪一段"。

## 良定义问题与病态定义问题

课件连着两个『Well-defined problem / ill-defined problem』页给出这两个定义，字面几乎是镜像的：

| | 定义 | 能否在问题空间里表示 | 课件例子 |
|---|---|---|---|
| **良定义 Well-defined** | 对提供的数据、动作、策略、目标状态有**完整规定**（full specification） | **能** represented in a problem space | *find the bug*（找一个 bug） |
| **病态 Ill-defined** | 对数据、动作、策略、目标状态只有**部分或不精确的规定**（partial or imprecise specification） | **不能（完全地）** be (entirely) represented in a problem space | *mission statement*（使命宣言） |

### "找一个 bug"为什么是良定义的

课件给出的形式化骨架是一个条件分支：

```
if (<boolean expression>) {
    S1 ;
} else {
    S2
}
```

配合的说明页写着 **missing semicolon**（少一个分号）。意思是：**给定这段代码，缺陷就是"else 分支末尾少了一个分号"** —— 数据（这段代码）给全了，可行的动作（改哪一行、写成什么）给全了，判定"改好了"的标准也给全了。**这是一个能被程序验证器查出来的问题。**

### "使命宣言"为什么是病态的

*mission statement* 里没有可执行的数据、没有动作清单、也没有"算成功"的判据。**它是意图，不是问题。** 从它到"问题空间"之间缺的不是努力，是一次**目标分解**（把 "扩大市场份额" 压成 "两年内 5%"），而这一步做完往往就已经产生了一个良定义问题。

> [!tip] 类比
> 良定义问题像**编译错误**：编译器能告诉你行号、列号、期望的符号。病态定义问题像**"这个软件不好用"**：没有行号，得先做出判断才知道错在哪。设计者做的事，本质上是**把后者翻译成前者**。

## 一句话收束

> 问题空间 = 目标状态序列 + 每步所需信息；解题 = 让当前状态 X 挪到与期望状态 Y 重叠；现实里停手在"够好了"的位置；而把病态问题变良定义问题的唯一办法是目标分解。
