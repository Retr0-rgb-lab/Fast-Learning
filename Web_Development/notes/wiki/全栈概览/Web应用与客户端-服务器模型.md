# Web应用与客户端-服务器模型 · The Client–Server Model

> **一句话**：整门课只反复训练同一个模型的两端——**客户端负责要，服务器负责给**，而两端之间唯一的共同语言是 HTTP，所以把 HTTP 学会，就等于学会了这个 Web 世界里所有的交接方式。

课件原文见 [Lecture_01_Overview.pptx](<../../raw/Lecture_01_Overview.pptx>)。本篇覆盖其中 "The Big Picture" 一节的前两页：The Client–Server Model（客户端—服务器模型）与 One Request, End to End（一次请求的全程）。

## 一、模型的两端各干什么

这个模型的全部内容就是下面这张表。左边一列是**谁来提要求**，右边一列是**谁来满足**，中间那一行是它们交换的东西。

| | 客户端（Client） | 服务器（Server） |
|---|---|---|
| 具体是谁 | **浏览器（browser）** | **Web 服务器（web server）** |
| 干什么 | 渲染（render）页面、运行 JavaScript | 存放资源、提供文件、执行业务逻辑 |
| 三种内容各管什么 | HTML 管结构（structure）、CSS 管样式（style）、JS 管行为（behaviour） | 收到请求 → 找到/算出结果 → 回一份应答 |
| 规模关系 | **一对多（one-to-many）** | 一台服务器可以同时服务成千上万个客户端 |
| 唯一的共同语言 | **HTTP** | **HTTP** |

课件在这一页上给的客户端标签是"野外最常用的五种浏览器"，给服务器标签的是"今天在用的 web server 举例"——**这两个清单是图片，不在文字稿里**，要逐个看是哪几个，得翻 PPTX 原件。文字稿能确认的只有它们的角色，不是个案名单。

> [!important] 一对多是模型的核心
> "数千个客户端可以和同一台服务器对话"（Thousands of clients can talk to the same server）。这句话决定了后面几乎所有的工程决策：既然客户端不可控、数量不可预知，服务器就必须假设自己随时会被无数来源同时敲门——这正是 [[后端技术栈]] 里 Node.js 那种非阻塞、事件驱动模型存在的理由。
>
> 反过来，"客户端"也不等于"人"。同一个服务器面对的可能是手机、桌面、IoT 设备——[[性能与可扩展性]] 里写得更直白：能说 HTTP 的都算用户。

## 二、唯一的共同语言：HTTP

课件对"服务器要回答每一个请求"这句的补注是：

> Client and server speak one language: HTTP — you master it in Week 9.

也就是说，客户端和服务器可以是**完全不同的程序、由不同的人用不同的语言写的**（客户端是浏览器厂商的 C++ 程序，服务器是你写的 JavaScript 程序），但它们之间**只靠 HTTP 交接**。只要双方都遵守 HTTP 的格式，谁实现成什么样都不影响对话。

这带来两个直接推论：

1. **换掉客户端不影响服务器。** 你的服务器不需要知道来的是 Chrome 还是 Safari，它只需要发出合法的 HTTP 响应。
2. **换掉服务器也不影响客户端。** 浏览器不知道对面是 Node.js、Java 还是 nginx，它只检查状态码和响应头。

> [!warning] "一个协议"不是"一个简单协议"
> 课件在 HTTP 那一页的收尾特意强调："One protocol, every exchange, all semester"——全学期每一次交互都是同一个协议。**但它同时标注 Week 9 才深入（goes deep）**，所以 Week 1 这里只需要接受"只有一种语言"这个事实，不要现在就试图学完 HTTP 规范。请求和响应的骨架见 [[HTTP与URL]]。

## 三、一次请求 = 一个循环

课件的措辞是：

> Six steps happen every time you type a URL — the web is this loop running millions of times per second, worldwide.

把它压成一句话就是：**你在地址栏敲一次回车，Web 就跑一遍"请求进、应答出"的循环；这个循环全球每秒跑几百万次。**

| 你看到的现象 | 模型里对应的事 |
|---|---|
| 敲 URL、按回车 | 客户端发出一个 **HTTP request** |
| 转圈 | 服务器在处理这个请求 |
| 页面出现 | 服务器回了一个 **HTTP response**，客户端把它渲染出来 |
| 再点一个链接 | 同一个循环再跑一遍 |

> [!note] 关于"六步"
> 原文这一页确实宣布了 **Six steps**（六步），但六个步骤本身是画在**示意图**里的，PPT 的文字提取拿不到，**因此本篇不替它列出那六步**。需要逐步对照时，直接打开 [Lecture_01_Overview.pptx](<../../raw/Lecture_01_Overview.pptx>) 看这一页的图。
>
> 文字稿能确证的只有循环的两端：**请求进来、应答出去**，而 **HTTP 要到 Week 9 才拆开讲**。中间步骤请以 PPT 原件为准，不要采信任何二手转述（包括本篇）。

## 四、这个模型如何长成整门课

Week 1 之后的每一周，都是在这张表的一格上加东西：

| 课程周次 | 在往哪一端加 |
|---|---|
| Week 2–5 | 加客户端那一端：HTML、CSS（见 [[HTML是什么]] 起的整条 HTML 线索） |
| Week 6–8 | 加客户端的行为：JavaScript、DOM、事件 |
| Week 9 | 把唯一共同语言 HTTP 拆开讲（[[HTTP与URL]]） |
| Week 10–13 | 加服务器那一端：Node.js、Express、数据库、部署、性能（[[后端技术栈]]） |

所以这张表是**目录的目录**：[[课程路线图]] 里的周次表，本质上就是这张表的两个格子分别被填满的时间表。

> [!tip] 复习这一个模型是否真的懂了
> 自测三个问题：（1）为什么服务器端可以用 JavaScript 写，客户端却不是？（2）为什么客户端数量多这件事会逼出"非阻塞"这种设计？（3）如果客户端和服务器之间换一种语言，浏览器哪一部分需要改？——三个都答得上，这一节就够了。
