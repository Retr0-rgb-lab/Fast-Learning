# 性能与可扩展性 · From Personal Sites to Web Scale

> **一句话**：大型网站不是"一个大程序"，而是**十几个各自能独立扩容的部件**——遇到瓶颈时**只扩出问题的那一块**（加服务器、加 Redis、加 CDN 节点、加 worker），这才是可扩展性的真正含义。

课件原文见 [Lecture_01_Overview.pptx](<../../raw/Lecture_01_Overview.pptx>)。本篇覆盖其中 "The Journey" 一节的四页（简单个人网站 → 大型部署 → 五层 → 独立扩容），以及 "Backend" 一节 Part IV 的性能要点。

## 一、起点：一个人能跑的最简网站

课件在讲巨头之前，先给了一个**最简单但真实存在**的网站：

> Just one of each — one browser, one domain, one server (files + CMS), one database.

| 部件 | 数量 | 说明 |
|---|---|---|
| 浏览器（browser） | 1 | 访问者的那台机器 |
| 域名（domain） | 1 | 别人能记住并访问到的地址 |
| 服务器（server） | 1 | **网站文件 + CMS**（内容管理系统）都在这一台上 |
| 数据库（database） | 1 | 存内容数据 |

课件给的访问链路是一条直线：

```
Visitor  →  HTTPS  →  DNS  →  Website files  →  Database
```

> [!note] 这条链路上已经有两个"以后会长大"的东西
> 链路里的 **HTTPS** 和 **DNS** 在这一页就被写进去了——它们在 [[HTTP与URL]] 里分别是 URL 的 scheme 段和 host 段，在这里则是**访问必经的两道关**。按 [[课程场景与阅读约定]] 约定的「示例站」（那张假想的课程主页），它现在就长这样：一个域名、一台放静态文件加 CMS 的服务器、一个数据库。这一页就是全库所有例子的**规模下限**。

## 三、五层：一次请求怎么走

课件把这些部件归成**五层**，并给每一层同样的三栏：里面有什么、这一层的职责、这一层要干成什么。

| 层 | 这一层做什么 | 职责（课件原话的中译） |
|---|---|---|
| **1　User's browser** | 你的电脑、手机、IoT 设备——**凡是能说 HTTP 的都算**；渲染 HTML/CSS/JS、运行 JavaScript、与服务器对话 | **Origin of every request**（一切请求的起点） |
| **2　Traffic management** | **DNS 把域名解析成 IP**；**负载均衡器把流量分摊到多台 Web 服务器**；**CDN 从靠近用户的边缘服务器发静态文件** | **Spread, secure, accelerate**（分散、保障、加速） |
| **3　Application** | **Web 应用服务器跑你的代码**；**作业队列 + worker 处理异步任务**；**全文检索服务处理关键词查询** | **Execute the business logic**（执行业务逻辑） |
| **4　Data & services** | **数据库存持久状态**；**缓存服务放热点数据（Redis）**；**微服务：鉴权、支付、消息……** | **Persist, retrieve, search**（持久化、取回、检索） |
| **5　Cloud & CDN** | **对象存储放文件与备份**；**数据仓库做分析**；**管道把事件流向 BI 看板** | **Bytes at scale, insights**（规模化字节、洞察） |

层与层的关系，课件一句话点明：**"A request visits them one layer at a time — each one with its own job and its own scaling knob."**（请求逐层经过，每层有自己的活儿和自己的扩容旋钮。）

对照 [[三层架构]] 就能看出这是同一条主线的放大：

| 三层架构（Week 1 早期那页） | 五层（旅程的终点） |
|---|---|
| CLIENT | 第 1 层 User's browser（**同一个东西**，只是被算进了架构里） |
| SERVER | 第 2、3 层 Traffic management + Application（**服务器被拆成了"管流量"和"跑代码"两半**） |
| DATABASE | 第 4、5 层 Data & services + Cloud & CDN（**数据库被拆成了"热数据"和"归档分析"两半**） |

> [!important] 拆分的动机不是"更先进"，是"各自能单独扩"
> 服务器从 1 台变成 N 台，数据库从 1 个变成"主库 + 缓存 + 副本"，是**为了让每一层被拆出来的部件都能各自加机器**。这就是下一页那个"关键想法"的预告。

## 四、关键想法：每块独立扩

这是整个 Week 1 最重要的一页。课件把扩容写成**四个症状 → 四个对策**：

| 出现的症状 | 课件的对策 | 为什么可行 |
|---|---|---|
| **Web 流量上涨**（Web traffic increases） | 在**同一个负载均衡器后面多加几台 Web 应用服务器** | 因为**应用是无状态的（stateless）**——任意一台都能独立处理任意请求 |
| **数据库成了瓶颈**（Database is the bottleneck） | 上**缓存服务（Redis）**，或**数据库副本** | **读被分散出去，写仍然留在原处**（reads fan out, writes stay） |
| **远处用户延迟高**（Latency for far-away users） | **把 CDN 推到边缘** | **静态资源（甚至 API 响应）都从附近的节点命中** |
| **异步或重活堆积**（Async or heavy work piles up） | **挪进作业队列 + 作业服务器** | **面向用户的路径保持快**（user-facing path stays fast） |

课件给的那行压缩写法：

```
web: +1 server   |   data: +Redis   |   edge: +CDN node   |   async: +1 worker
```

> [!warning] 无状态是前提，不是结果
> "加机器"这件事**只对无状态的应用成立**。如果会话状态只存在某一台服务器的内存里，那台服务器就成了单点，加机器反而会丢数据。课件在这页没有展开怎么做到无状态（那属于 Week 11 的会话部分），但它是这条"独立扩容"路线的**承重墙**——记住这一点，后面读任何"上集群"的方案，先问它状态存哪。

## 五、性能三件套（Part IV 的补充）

旅程走到能扛流量之后，课件的 Part IV 给出三件具体的事，本篇只列要点（展开见 [[后端技术栈]]）：

| 手段 | 课件的定位 | 落在上面哪一层 |
|---|---|---|
| **缓存（Caching）** | `Cache-Control` 头、ETag、服务端缓存（Redis）——**把答案留在近处，回访跳过重复计算** | 第 2 层（边缘）与第 4 层（Redis） |
| **CDN** | 静态文件的副本放在**全世界的边缘服务器**，从**离每个用户最近的**那个发出 | 第 2 层与第 5 层 |
| **HTTP/2 与 HTTP/3** | **多路复用**（一条连接跑很多请求）、**头部压缩**；HTTP/3 进一步走 **QUIC/UDP** | 贯穿第 1↔2 层的那一跳（[[HTTP与URL]]） |

课件在这一组里还留了一句工作方法，比任何单项技术都更该记住：

> Measure first — Lighthouse and the Network tab give you numbers — optimize what the data says, not what you guess.

**先测量，再优化；按数据下手，不按猜测下手。** 测量工具就是浏览器开发者工具里的 Network 面板与 Lighthouse（见 [[DOM与开发者工具]]）。
